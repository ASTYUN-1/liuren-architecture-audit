# liuren_compute 参数接口修复

当前活动版本：`20261106-compute-interface-10`。父版本09完整保留，未就地修改冻结运行包。

## 实际故障

从本机OpenCode数据库以只读方式查到同一会话的三次calendar失败。仅保存了相关工具参数和报错，未导出原问、课盘、推理正文或其他会话内容。记录见`observed-calendar-failures.json`。

三次参数分别为：缺少day_boundary、day_boundary="midnight"、day_boundary={type:"midnight",at:"00:00"}。旧错误均为`explicit Asia/Shanghai timezone and day_boundary required`，没有指出合法枚举值。

根因是09版的原生工具schema将calendar声明为unknown，模型实际看不到start/end/timezone/day_boundary等必填项及其类型，packet中的计算请求也有同样问题。完整说明虽在资料中，工具本身未充分暴露结构。上一轮90项测试验证了正确参数、事实计算和文件交接，遗漏了这一层参数暴露检查。

## 修复内容

- 将calendar改为明确对象schema，直接显示四个必填字段、合法换日枚举、可选筛选和日内取样字段。直接查询和packet的computation_requests共用定义。
- 合法day_boundary仍只有字符串`civil-midnight`（00:00换日）与`zi-hour`（23:00换日）。不静默替模型选口径，不将不明输入自动改成默认值。
- 原生执行入口也校验参数，错误提供具体字段路径、合法值和最小调用示例；底层日历错误同样说明正确写法。未知日期字段不会被静默忽略。
- expression同步改成可见的数值/查表/四则运算递归结构，保留原程序深度、节点、数表与精度限制。
- 主、子智能体提示补入实际参数及纠错规则：按字段更正一次，仍失败则记录具体计算缺口；不反复猜格式，不手算日期冒充程序核验，不因此自动改判成败。

正确结构示例（日期只是结构示例，实际范围依据本问）：

```json
{
  "action": "calendar",
  "calendar": {
    "start": "2024-01-15",
    "end": "2024-02-05",
    "timezone": "Asia/Shanghai",
    "day_boundary": "civil-midnight"
  }
}
```

未改变原排盘算法、专业方法正文、书据、14项必查、16专项、11原环节覆盖或裁决模型。DeepSeek V4.1 Flash、high及oh-my-opencode-slim保留。经验库和案例库仍关闭，没有增加模型调用环节。
