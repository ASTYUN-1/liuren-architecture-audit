# 当前六壬 Skill 的核心作用与精简审查

审查日期：2026-11-07。基线：`20261106-performance-25`。本轮只审查与提出候选方案，没有改活动包、入口、工具、排盘算法或网站，也没有调用付费裁决模型。

## 一、先确定它究竟要完成什么

这套 Skill 的核心作用是：**让模型利用可信的程序课盘，理解原问，正确选择和运用专业方法，综合课传、关键类神及其有效作用，形成有依据、可复核的逐问判断。**

它应重点解决五件事：

1. 问的是什么事、涉及谁或什么、怎样才算回答了问题。
2. 本问应取哪些对象、位置和专法，而不是看见什么名象就讲什么。
3. 各关键节点怎样相互作用，力量、通路、空墓、制救及结构怎样影响结果。
4. 哪些支持成立，最强反证是否改变结论，尚缺什么。
5. 把结果、依据、条件和所问精度交付清楚；应期和数量按原问触发。

所以，精简的优先准则是**提高上述任务的完成质量和效率**。字数减少、文件减少、调用减少只是结果指标。完整性也应指必要知识和判断覆盖完整，不应等同于固定读满14个文件或写出32项核查台账。

对每段内容采用以下判断：

| 内容实际作用 | 处置原则 |
|---|---|
| 提供不可替代的取用、效力判断、专法条件或关键反例 | 保留；组织到真正需要它的位置 |
| 防止仍可能发生的重要误判 | 保留一条明确规则；重复案例按需查看 |
| 程序已确定完成的计算、定位与采用决定 | 由程序输出结果和状态，模型直接使用 |
| 重复总纲、旧版补丁、研究过程、历史差异、维护步骤 | 移出日常执行；必要证据原件继续保留 |

不能用“看起来更专业”“此前要求必读”作为永久保留理由，也不能只凭“字多”删掉专法条件。

## 三、最值得先做的精简

### 1. 神煞：取消模型复核确定性起法，保留并加强取用知识

用户提出的方向成立。当前程序已经有38条固定规则和22个停用名称；`resolveShensha`输出采用状态及`places.tian/di/jiang`。新盘通过修正层输出facts及归档，交接时又由程序生成`adopted_shensha`。正常程序盘无需模型重新核岁/月/季/日/旬公式，也无需每课比较旧引擎和古籍异法。

但当前三个必读页仍混合了这些任务：

- `engine-shensha-output.md:18–21`要求输出、起法、取用三层判断，起法层要求核历法、文献和定义。
- 同页`:25`以后要求保留旧病符、吊客、天地医差异，后文又确认新输出已修正。
- `shensha-focus.md`的大表同时放“原有覆盖”“新增/校正”“起法”“使用边界”“来源”。
- `shensha-use.md:27`仍要求模型读完整12宫、核起法和登记上述差异，而`:7`已明确采用程序固定结果。
- `shensha-tradition`和旧`daliuren-shensha`又保留相似说明、旧表及推演。

这不是三个步骤各自不可替代，而是计算、修订史和使用方法没有彻底分开。

建议把日常模型需要的内容收束为：

> 直接使用程序给出的神煞ID、名称、可用状态、所属天盘、所临地盘和乘将。对切题项依据其象义、对象、阶段、气态及组合条件判断作用，纳入全局生克制救。不重算起法，不比较旧表，不把停用或缺参项当作依据。

相应分工为：

| 工作 | 由谁承担 |
|---|---|
| 32项及补充规则是否完整输出、位置计算、别名与停用状态 | 程序一次完成，保留机器记录 |
| 稳定名称、实际位置、输入缺口的传达 | 一份清楚的程序结果 |
| 什么情况下有关、代表什么、能起何种作用 | 模型读取取用知识并判断 |
| 起法异传、旧引擎差异、权威复核过程 | 维护与研究资料 |

**不建议简单删掉神煞取用。** 程序算出天医在哪里，仍不能决定天医是在救患者、伤患者、助病鬼，还是与本问无关。取用规则和综合判断正是Skill要提供的价值。

也不建议把32项改成仅有几个关键词的封闭筛选。可让程序保留全项覆盖和全盘位置，模型重点解释本问类神、课传、相关年命及能改变结论的组合；切题的清单外作用仍可进入。这样减少机械抄表，保留发现关键作用的能力。该组织变化仍需回归观察遗漏情况。

### 2. 八煞九宝：保留覆盖作用，取消重复执行阶段

`bashajiubao.md`中的合、刑冲破害、墓、鬼、空、生旺等，已经在`relations/liqi/void/structure/movement`承担判断任务。德禄马奇仪贵又与神煞知识重叠。

应把它用作**同一次分析的查漏范围**，将独有规则归入相应方法。无需在理气之后再以“八煞九宝”为名重做一轮。删除独立步骤不等于删掉这些关系和条件；“八煞九宝”也不应被当作一张纯神煞名单整体弃用。

### 3. 把共同分析写成一条主线，停止按文件反复启动

目前定位、关系、理气、空亡、动态、风险、神煞和报告中多次要求：明确对象→查状态→查生克与通路→查制救→查反证→回核主线。同一要求在不同文件出现，不代表应重复完成。

建议合成一次连续分析：

> 原问和可信盘 → 按占类取用、确定侧重 → 在课传中综合判断关键节点及作用 → 检查最强反证与未决条件 → 逐问交付。

分支在需要处接入：分类细法在取用处接入，神煞与课体的特殊组合在相关节点接入；年命有明确输入且需要时接入，应期/数量有任务时接入；原书只有真实知识缺口时补查。

这条线不应变成“先固定成败，再补细节”。新取用或有效反证改变关键条件时，仍重核受影响的作用。

### 4. 通用知识只写一次，具体条件留在专项

可明确精简的实例：

- 十二天神与十二天将共24个义项，重复同一79字符“待辨”段。仅此一段集中一次即可减少1,817字符，尚未计共同适用和边界模板。
- 人际、求职、升薪重复C07“人职与总分关系”；求职和升薪又重复C08/C09/C15；音信规则在多个占类出现。
- `structure`和`movement`常以方法说明、执行步骤、失败模式三次叙述同一条件；应合成“触发条件—判断作用—例外”，例证按需查看。
- 六个方法文件重复同一程序事实接口说明；可在共同入口说明一次。

但不宜把16专项全部并成一份大文件，也不宜让每条规则都再跳一个文件。更合适的实现是：**共同规则单源维护，程序按所选占类装入一次完整适用规则**，既去重，又不增加模型的手动跳转。

例如求职和升薪可以共用组织取用知识，但应聘、录用、升职、调动、净收入的独有条件不能互相替代。胎产的干儿支母、婚配的专项对待轴、失物与盗捕的对象差别都属于必须保留的内容。

### 5. 已选定的算位异法退出运行；未选定的断法问题分别处理

神煞固定表已经明确选择，日常只需要采用结果和身份，天医辰起与旧表等差异不必每课登记。当前政策表、测试和研究证据可继续保存，不让模型在每盘重新选法。

另有一些内容并非固定排盘问题：

- 空亡遇生扶时是否可实现，当前`void`仍保留互有张力的断法。
- 财通类/专类俱现、财不入课传的主次，`finance`仍标未决。
- 旺鬼贪荣、鬼禁日以及制救时序，当前裁决依据仍分别处理。
- 确定性状态接口仍提供两种五气口径，程序没有替模型选定全部采用条件。

对于这些，应在知识维护时决定项目采用什么方法及适用范围，然后把**已定执行规则**交给模型。不能仅删除差异说明，就把尚未决定的方法伪装成固定标准。无需在普通占断中展开考据史，但仍须提供会改变判断的适用条件或明确限制。

### 6. 旧版补丁和接口说明应退出专业提示词主体

已确认的问题包括：

- 第24、25版的长段同时存在于Skill入口、AGENTS、高效执行、程序接口参考和可选审计模块，且分别要求检查`liuren-tools-24/25`。应只保留当前协议的单一说明。
- “报告传输边界”同一403字符段在审查集合内出现7次。它约束交接，不应反复占据专业方法正文。
- 自动加载的《本机OpenCode完整输出规则》仍保留旧12版“程序提示亲属标签冲突”“结构化结果”等说明；当前代码和自然事件定位规则已变。
- `references/adjudicator-prompt.md:21/46`仍要求application与output-v2等结构；当前slim实际prompt和提交代码已接受自由正文。现查运行链未发现该参考页被直接作为裁决提示载入，所以不能说实际裁决者必然收到旧要求；但它属于可被误读的陈旧副本。
- `deterministic-tools.md`前文还列固定timing.record/quantity.record等旧返回字段，后文又声明自由报告。

应把**如何传输与失败恢复**交给当前工具schema和next_call；专业提示词只保留最短成功路线及职责。hash、归属、容量、完整文件等仍由程序校验，模型不需要反复解释这些机制。`contractChecked`也不应被描述成术理正确性的验收。

### 7. 报告围绕判断价值组织，工程台账自动附带

报告的核心是：直接回答各问，说明取用、关键作用、最强反证、条件和精度；有应期或取数任务时解释其方法。

当前`report`另要求32项核查状态、必读模块、实际读取、裁决agent/model/request_id等。若这些信息需要保留，可由程序生成技术附录，避免模型反复写操作流水。**提示词精简不等于把完整技术报告改成几句话**；决定性依据仍应充分展开，同一理由只解释一次。

### 8. 维护流程保留能力，与占断主线分开

`procedures/liuren-cases`、`liuren-extract`服务于归档、复盘、知识提取，本身有用途，不能因普通研判不调用两库就删除。

当前入口已经把它们分流，不能把两份规程的全部字数算成每课开销。优化重点是：维护共用保存、来源和验证约定只写一次；普通占断不因这些链接转入知识整理。研究证据、hash映射、历史勘误也按同样原则退出默认读取。

## 四、实际跳转是怎样产生的

当前调用链可归纳为：

1. `AGENTS`、主智能体prompt及三个instructions文档形成常驻规则。
2. 加载`daliuren/SKILL.md`，按三阶段读固定方法与本问分类。
3. 用`liuren_chart`取得可信盘和程序事实；必要专法调用`compute`，知识缺口才查书。
4. 保存packet时，程序检查13个准备必读模块及所选分类的全文回执；report在交付前另查。
5. packet自动装入定位、分类及有任务的应期/取数全文，并将所交方法装成裁决文件；同源同段全文已有别名去重。
6. 独立裁决者以自己的配置和文件材料裁决；主智能体领取、核事实/引用/覆盖并交付。

重要区别：

- `action=method`只返回所选模块正文和依赖元数据，不会自动递归打开全文里的所有链接。多数参考跳转是模型根据文案继续选择的。
- 旧`plan_steps`会展开声明依赖并去重；当前普通读取不要求先跑旧批次计划。
- 固定14项并非只有文案要求。`tools/liuren-flow-control.mjs:39–48`会查必读回执，packet插件执行前调用coverage。**只删提示词步骤、不同步路由和门禁，会被程序要求补回旧模块。**
- 两个模型分别读必要知识，是两个独立上下文的需要，不能把所有跨角色重复都当无用。可以减少材料内部重复和主智能体重复判断，但必须保证裁决者收到完整的必要知识。
- 当前已经有方法合批、已读复用、同源别名去重和计算回执复用；这些不是尚待实现的新建议。

因此后续优化需同步入口、三份自动加载说明、实际主/子prompt、路由/manifest、回执门禁、材料装配与测试。活动冻结包保留，候选另建；不能只改五目录里的某几个Markdown就认定完成。

## 五、候选组织方式

不必先追求把59个模块变成某个固定数字。建议从功能上形成以下结构：

| 功能 | 模型何时取得 | 应有内容 |
|---|---|---|
| 短工作流 | 开始时一次 | 核心目的、主线、分支条件、分工及最短交接 |
| 共同判断知识 | 完整研判一次 | 取用、关系效力、气态、空亡、结构、阴神、制救与反证的共同规则 |
| 本问专项 | 确定事件时 | 该占类独有角色、目标、成败条件和特殊组合 |
| 神将/神煞/课体字典 | 知识需要处 | 含完整适用条件的相关义项，不携带旧引擎起法史 |
| 时间/数量/年命分支 | 实际任务和输入触发 | 所选方法及必要例外；计算交程序 |
| 来源与维护 | 真实缺口或明确维护任务 | 连续原文、分歧、勘误、hash及历史记录 |

这既保留一条工作流，也允许必要知识按分支进入。短提示词不应退化成“请综合判断”一句话，再让模型凭自身印象补回被删的专业内容。

目前独立裁决架构先保留。若以后比较单模型直接分析，可以作为单独实验方向；它同时改变判断主体、上下文和复核机制，不适合混在第一轮无损精简里宣称同等准确。

## 六、怎样做到提效而不降低判断质量

第一轮应优先做用途明确、专业含义不变的整理：合并重复约束；消除旧协议；确定性计算回程序；研究史与维护文档退出默认路由。第二轮再调整32项模型检视方式、专法切片和主/裁决材料分工。后一类会改变模型注意力，风险高于删旧补丁。

每个候选须建立旧内容到新位置的对应：**具体规则、触发、例外、保留原因和新加载位置**。不能以“意思差不多”替代对照，也不以压缩后结果与旧版一致证明专业正确。

建议分开验证：

| 目的 | 怎么检验 |
|---|---|
| 证明机械冗余确实减少 | 比较实际载入字符/token、方法/阅读/计算次数、传输页数、无效参数与恢复次数 |
| 确认程序事实不被模型重算 | 使用同一课盘归档，检查模型是否直接使用同一坐标、采用状态和计算回执 |
| 确认必要专业知识未丢 | 人工按规则映射核触发、条件、例外及关键反证；检查子问是否答全 |
| 发现注意力变化造成的退化 | 同模型与设置、同背景和课盘，成对比较旧/候选，多次运行；独立审查关键遗漏与无据断言 |
| 评估预测准确率是否保持 | 另外使用未曝光且反馈可核的样本，预先固定问项、结论精度和判验口径，比较结果与不确定范围 |

建议的代表任务：代问考试；疾病中患者/病象/医救相反作用；财务中成立/到账/金额分问；婚恋或胎产的专项对待轴；行人多候选日；同卦追问和缺年命输入。已曝光资料可作开发回归，不能因此变成独立盲测。

审查工具已生成`benchmark-starter.json`，没有运行真实模型。通用插件脚手架不能直接替代本项目OpenCode双角色评测。正式测量还应确定三项高价值任务、必须通过的全链任务、报告产物、可核验命令/人工判据和边界样本；上述代表任务可作为初始选择。

目前可确定的是：存在大量功能重复、程序职责回流和过期协议，足够支持一轮精简。**尚不能据静态审查保证任何候选版本的预测准确率不下降，也没有已测得的加速比例。**
