# 裁决材料保存失败：17版修复

## 实际日志与根因

只读检查本机OpenCode数据库中最新对应会话。方法读取回执明确为16版，不能把此次失败归咎于用户没有加载新版本。该会话共调用19次 `liuren_adjudication_packet`，13次失败，其中9次返回 `LIUREN_ADJUDICATION_CONTRACT: input identity`。原始调用及原问/方法读取记录在本目录留作本机故障证据，含个人问题背景，不作公共测试夹具或Git交付。

1. **请求编号存在未公开的限制。** 原程序把请求编号也限制为字母开头，因此拒绝了 `20261106-…` 和部分数字开头UUID。原生工具schema只写string，没有公开该约束；报错又把schema和编号合成“input identity”。日期编号不涉及专业判断，也不是材料数量错误。模型却不断删减事实、观察、争点、未知和来源作探针。
2. **当前方法文件的来源交接不够直接，报错也缺定位。** 第一份完整调用提供了当前runtime文件路径和SHA256，仍因未写行号被拒绝，且没有指出哪条材料缺范围。模型由此额外读取文件、补行号。
3. **装配容量存在真实缺口。** 修复前两项后，原始完整参数经程序补入可靠课盘、完整方法和日历计算，共约13.1万字符，超过旧10万上限。该问题此前被编号错误遮住；如果只改编号，完整包仍会失败。

另外几次失败来自探针调用中改错归档路径/hash或清空实体。这些检查继续保留，不能为使空探针通过而放松课盘完整性或哈希校验。此前回归未覆盖“日期编号＋这份真实装配体积”的组合，本轮已补充对应回归与真实参数重放。

## 具体修复

- 请求编号允许首位字母或数字，共1—128位ASCII字母、数字、下划线、短横线；日期编号和UUID原样保留，不自动换ID。禁止路径分隔符。原生schema同步公开同一正则和示例。
- schema错误与编号错误分别指出 `packet.schema`、`packet.request_id`，编号错误说明合法值、实际值和只改该字段。数组与容量错误报告实际数量和边界；行对象ID错误给索引。
- 当前runtime方法在manifest和实际hash通过后，可以只传路径和已知hash，程序装入完整正文。不扩大到任意文件。书籍仍须准确连续行段，范围报错给材料ID、路径、起止行、合法范围和行号口径；不能用摘要冒充引文。
- 程序扩展后的总输入上限调整为20万字符；UTF-8文件上限同步为70万字节，保存和读取一致，超限明确报错而非静默删材料。并非要求每问装满这些容量；原有按需选资料原则保留。
- 主Skill、工具说明、交接方法和主智能体提示明确：按具体报错字段修复，不删事实、观察、争点、未知去猜原因，不换归档hash、不以空包反复probe。确定性计算、完整盘和全部专业规则保持。
