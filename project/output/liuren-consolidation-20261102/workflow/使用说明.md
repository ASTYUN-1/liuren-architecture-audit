## 先检查环境

在项目根目录执行：

```powershell
python -X utf8 tools/liuren-workflow.py doctor
```

也可从任意当前目录调用项目的 `verify-system.ps1` 或 `verify-system.bat`。它们只是上述只读检查的代理，不启动服务。旧代理原文件位于 `归档/配置与旧说明/融合前-20261102/`。Node.js 与 Python 是系统依赖，不随资料包复制；doctor 显示实际程序路径。`start-server.bat` 保留原用途：可选的本地图形排盘界面（3456）。

## 新任务

输入 JSON 示例：

```json
{
  "chart": {"datetime":"2026-08-04T14:32","label":"offline"},
  "source_id":"",
  "exclude_sources":[],
  "questions":[{
    "id":"Q1", "question":"何时收到多少款", "target":"收款", "stage":"实际到账",
    "success_criterion":"到账日期与金额", "requires":["conclusion","timing","quantity"]
  }],
  "domains":["finance"],
  "modules":[]
}
```

`questions` 由研判者按题目明确登记，程序不声称自然语言拆问完备。所有问题至少要求 `conclusion`；有时间或数量问题分别加 `timing`、`quantity`。已知原案编号、同案路径和转引身份须写入 `source_id` / `exclude_sources`，不得把保留答案放进公开输入。未知同案联系仍可能漏排，须人工检查污染风险。

```powershell
python -X utf8 tools/liuren-workflow.py prepare --input INPUT.json --out RUN
```

RUN 必须是新目录。prepare 调用现有固定引擎并检查原盘，产生 `context.json`、`evidence-packet.json`、`coverage.json`、`session.json` 和 `reads.json`。`context.json` 是模型需要的盘面、子问、哈希与模块计划；`session.json` 含本地证据快照，不应反复整份送入模型。候选包只作召回，省略的候选编号保存在 coverage.json，候选清单用稳定哈希确认。

先按原十一环节读取计划模块的所有页，然后读相关条目：

```powershell
python -X utf8 tools/liuren-workflow.py read --run RUN --id module:positioning --page 1
python -X utf8 tools/liuren-workflow.py read --run RUN --id LR26-条目编号 --part record --page 1
python -X utf8 tools/liuren-workflow.py read --run RUN --id LR26-条目编号 --part evidence:0 --page 1
```

条目返回 `available_parts`、`page`、`pages` 和该部分哈希。`record` 保留完整结构与逐个证据定位，证据原文改从 `source`、`evidence:N`、`source_case:N` 分页读取；不会为读一张来源卡回传整本多案书。所有页均读完才算该部分的程序凭证；凭证只表示内容已输出，不证明人或模型理解了它。

默认检索和采用排除暂停记录；显式 `read --review` 只用于审查身份隔离后仍可见的暂停记录，不允许采用，也不放宽同案排除。会话以外的 ID、同案及保留答案无法通过按 ID 读取加入采用清单。普通旧 search/load 脚本保留为兼容定位；旧 `opencode-case-batch.py prepare/run` 已停止作为新执行入口，`status` 和历史档案接口保留。

## 记录条件，再检查

判断 JSON 顶层保留 `session_id`、`session_sha256`、`facts_sha256`、`stage`，逐问保留原 `id`。每项 conclusion/timing/quantity 记录 status（supported / conditional / unknown）和 statement；unknown 列 missing，conditional 列 unresolved。时间另列 window/trigger/basis，数量另列 range/unit/basis。支持性事实用 `chart_evidence: [{"path":"facts.day_stem","value":"庚"}]`，程序检查字段与原值相等。

规则应用项 `rules` 逐条记录：

- id、decision（adopt / conditional / reference / defer / reject）。来源方法 `source_method` 不是通用预测规则；没有辨明可迁移条件时只能 reference。
- conditions/exclusions 每条保原 index/text，标 role：source_context（原案背景）、source_outcome（原载结果）、applicability（可迁移条件）、exclusion、unknown。
- 前两类只准 `status: source_only`、`used_as_current_fact: false`、无当前 fact_refs，并写 transfer_rationale 表明历史参照边界；不把原案结果变成本案先验。可迁移/排除条件用 met/unmet/unknown；非 unknown 项给程序 fact_refs 和迁移理由，unknown 列 missing。
- application 给当前子问的 rationale/fact_refs；evidence_parts 列实际读完的证据段；source_refs 与会话已核对的源路径集合一致。
- strongest_counterexample 记录 addressed（assessment/source_refs，已登记反例还须 case_ids）、unknown（missing）或 none_registered。未知反例或未满足/未知前提不能 adopt。

`coverage.candidate_manifest_sha256` 填 context 中的覆盖哈希，`unreviewed_limitations` 明确保留未读、未评估及语义缺口；独立验证增量保持 0。

```powershell
python -X utf8 tools/liuren-workflow.py check --run RUN --record JUDGMENT.json
```

会话、程序、方法或来源变动时应重新 prepare。check 可检出缺页、来源与依赖变动、事实原值不符、缺子问/时间/数量、暂停或会话外采用、未知前提直接采用等错误。完整示例以本目录离线验收的 `acceptance-run/judgment.json` 为准（验收生成后可读）。

检查通过只说明本检查器覆盖的结构、身份、原值和状态约束通过。非空文字、来源相符和实际读过均不能证明术理推导成立，更不证明预测准确；现实结果及独立验证另行核对。最终固定程序盘链路及示例判断以 `offline-acceptance.json` 指向的 `acceptance-run-final2/` 为准；早期会话保留为构建过程记录，换版本后不继续用于交付。
