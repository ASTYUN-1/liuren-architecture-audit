# 本机与网站实际工作流程对照调查

调查于2026年11月1日晚开始，11月2日整理。线上方法及源码证据采集于北京时间11月1日23:53—23:57。本轮只调查：没有修改业务代码、参数或技能，没有发布、重启或运行新的解读任务；仅增加本地诊断脚本、脱敏收据和本报告。

## 结论

**专业主干相符，当前版本和执行流程不完全相符。**不能把网站看成“把当前本机原流程原样搬到服务器”。

两边均按“明占类→定侧重→看显象”、十一环节、13个基础必读模块执行。但本机已激活`20261027-quantity-02`及本机直接排盘覆盖规则；网站仍使用`20261023-modular-03`，并增加独立输入整理、分页取证、逐问结构化判断和交付门禁。

本机实际取样也没有显示“少读基础方法”或“使用多子智能体”是速度优势来源。真实差异集中在模块更新、工具传输、判断记录、检索边界和最终交付。

## 调查依据和范围

- 本机：项目`opencode.json`、`.opencode/liuren-active.json`、实际分组入口`.opencode/skills/liuren/daliuren/SKILL.md`、当前方法包、加载器、排盘工具及检索脚本。
- 实际使用：只读OpenCode数据库中本项目最近6个顶层会话的模型及工具元数据。5个加载了daliuren，另1个为排盘工具探测；其中4段具有完整方法读取路径。没有导出客户问题、报告或模型思维内容。
- 网站：通过严格主机指纹SSH读取当前worker进程的实际工作目录、资料根、协议、模块正文和资源指纹。不是用项目根web待审版本代替生产。
- 当前代码为`/opt/wenheng/releases/20261101-runtime-notices-01`；251个src文件整体指纹仍与本地调查候选一致。worker实际资料根为`/opt/wenheng/resource-releases/20261023-liuren-modular-03`，协议`liuren-v3`。
- 网站历史任务没有完整逐工具时序。本次比较能证明当前规则、实现及部分实际行为，不能证明每份历史报告都完全遵循了每个专业步骤。

## 一、方法和版本是否一致

| 项目 | 本机 | 网站 | 判断 |
| --- | --- | --- | --- |
| 当前方法版本 | 20261027-quantity-02 | 20261023-modular-03 | 不一致 |
| 三步主干 | 明占类、定侧重、看显象 | 相同 | 一致 |
| 主流程 | 十一环节，第9环节为应期与取数 | 十一环节，第9环节仍为应期 | 主干一致，环节内容已发生更新 |
| 基础必读模块 | 13个 | 相同13个 | 名单一致；其中理气、报告正文已更新 |
| 当前模块数量 | 49个 | 47个 | 本机新增2个 |
| 共有47个模块正文 | 41个与网站一致，6个更新 | 与本机旧版20261023-modular-03的47个模块全部一致 | 网站保留旧版，并非全套资料均有差异 |

6个更新模块为：考试`exam`、财运`finance`、失物寻人`lost-person-object`、理气`liqi`、报告`report`、应期`timing`。

新增2个模块为：`quantity`数量与精度、`quantity-sources`数法来源与条件。

具体影响：

- 本机在用户要求金额、分数、数量、距离等时，有独立的数量模块和条件路由；网站没有同步这两个模块。网站虽然允许登记`dimension=quantity`，也保留旧版数值约束，但不具备新版相同的模块阅读及核查路径，不能说网站完全不能处理数值。
- 新版应期补充事件起点、是否含当日、竞争轮次、六组检索导航及数理时长边界；修改了部分原论的适用表达。网站仍使用旧版。
- 财运、考试、失物寻人新版转接共用数量规程；理气和报告也增加了应期取数相关约束。不是单纯改版本号或展示格式。
- 本机`daliuren-paipan`操作实际被`docs/本机六壬直接排盘.md`覆盖；即使方法包原始排盘模块正文与网站相同，实际操作也不同。

方法版本指纹：本机`c92f8987e41b01824c2b64e73eeb7c5dc8afb26cfded19c7818d2ab5f750c24e`；网站所绑定本地方法版本`7dc4ea2003d7e5827ab75864b0fdb3e8736a40e848237fea5ebbed0d6159aa01`。

## 二、实际调用流程

| 环节 | 本机当前规则及已观察行为 | 网站当前实现 |
| --- | --- | --- |
| 理解起课意图 | 同一OpenCode会话理解用户描述，选择排盘参数 | 正式解读前单独进行一次高推理模型输入整理，签名确认后进入任务 |
| 排盘 | 优先liuren_chart；失败可转node tools/liuren-direct.mjs；归档完整原页面JSON | 服务端calculateChart生成或复用固定ChartSnapshot；read_case和calculate_chart向模型交付 |
| 占类和子问 | 在报告/小结中保留对象、目标和逐问裁决 | 必须register_questions，登记原文片段、对象、维度、成功标准、占类和条件 |
| 读取计划 | 本地plan或直接完整Read，二者允许等价 | 由register_questions返回readingPlan；必须通过read_knowledge读取 |
| 读取传输 | 近期样本直接Read当前方法文件，多文件同轮发出；也提供7600字节分页加载器 | 每次read_knowledge单页最多8000字节，首读后按deliveryHash补全部missingPages；可批量独立页，但没有“一次直接读全文件”的模型接口 |
| 检索 | 本地search-cases.py、search-experience.py，能选择数量、排除来源等参数 | search_cases、search_experience调用冻结索引适配脚本，接口范围和候选数量更窄 |
| 判断记录 | 可合并共享节点，直接输出逐环节小结和技术报告 | 每个子问都要提交record_judgment及完整11环节workflow数组、事实锚点、角色关系、反证和依赖 |
| 修订 | 按规则重评受影响结论，由模型在正文保持一致 | 修改问项或共享关系可使已登记判断失效，须重新提交相应记录 |
| 最后整理 | 采用本机完整技术报告，禁用wenheng-public-output | 普通用户报告还要prepare_public_output、分页读完公开输出规则，冻结分析后submit_report；专业模式免此公开输出阶段，但仍有判断和引用校验 |
| 交付失败处理 | 局部资料/检索失败可标缺，保留可靠盘的条件分析 | 必要流程、资料覆盖、引用或提交校验不满足，不能交付成功报告 |
| 上下文 | 同会话同版本完整已读模块允许复用 | 每项任务新建隔离进程、工作区和会话；追问传回旧报告及已成功问答，但不恢复上次模型会话和模块已读状态 |

不能把“分页”本身当作网站必慢的证据：本机也提供分页，网站也允许批量独立页。实际差异是本机样本主要直接读文件，而网站必须累计覆盖、结构提交和校验。

## 三、本机实际记录是否符合当前入口

最近6个顶层会话中：

- 5个会话的技能工具输出实际包含`20261027-quantity-02`，证明不只是active指针声明新版本。
- 4段完整研判读取路径都观察到13/13个基础模块成功读取，还按需读取占类、应期和部分条件模块。相关方法Read没有观察到截断标记或局部offset/limit参数；这仍不证明模型理解或正确应用。
- 这4段均为`deepseek/deepseek-flash`、`variant=high`。网站也固定`deepseek-flash`及高推理；当前全局默认另有模型，不能据默认值声称本机实际使用的是另一种模型。
- 实际读取存在一轮发出3—6个Read的批量行为；4段没有task工具调用。因此本轮没有证据把速度差异归因于本机启动了多个子智能体。
- 本机采用直接脚本检索，并非普通研判必须另开完整案例维护智能体。
- 多段记录先读一批方法，再检索、补条件模块；并非每份样本都严格按每个环节依次读取。记录只证明有实际调用，不证明流程顺序、内容采纳及判断质量全部合格。

另发现本机原生liuren_chart有报错后转CLI的记录；有些CLI调用只是查看帮助，不能把每次命令都算一次重复排盘。单次工具探测曾成功，尚不能据此认定当前工具必然损坏或已经修复。本轮未改该工具，也未作新的排盘复现。

## 四、资料检索是否相同

底层`case_retrieval.py`、`experience_retrieval.py`和`website-retrieval.py`三份脚本，线上正文与本机同名脚本一致。但使用入口不同：

| 项目 | 本机 | 网站 |
| --- | --- | --- |
| 索引 | 可根据现有源文件检查、更新本地运行索引 | 使用发布时冻结且绑定哈希的索引 |
| 案例数量 | 方法示例取6条，CLI默认8条，可调 | 单次结构检索最多5条 |
| 经验数量 | 方法示例8条，可调 | 最多5条 |
| 排除本案来源 | CLI支持exclude-source | 当前模型检索工具没有同等显式排除参数 |
| 占类别名 | 本地检索库较宽的别名规则 | 适配器预筛安全同义类，避免感情/胎产等混并 |
| 来源读取 | 读原档相关段和上下条件，必要时补全 | 引用前必须完整读完对应已发布文档或分段的全部页 |
| 检索故障 | 规程允许如实标缺后继续条件分析 | 成功交付门禁要求完成相应检索步骤 |

因此，相同检索底层不保证候选结果完全一致，也不保证两边每份报告读取相同资料。

网站资料清单有4099个交付文档/分段（231个case、88个experience、3780个reference），不是4099本书或独立案例。其绑定的496个独立源文件中，411个在本机同路径内容相同；84个属于旧运行包归档，映射到本机旧版后全部相同；另1份经验原档已变化。84个不是遗失资料，不能因目录重组就判作缺失。此比较仅覆盖网站绑定的来源，不证明本机新增全部资料已经上线。

## 五、排盘是否完全相同

线上实际加载的`lunar.js`、`data.js`、`api.js`、`guize.js`、`paipan.js`五份核心文件，SHA-256全部与本机相同，说明同源核心仍一致。

但是适配层不同：本机执行原页面JSON导出器并整理为`liuren-chart-facts-v1`，网站直接构建`ChartSnapshot`，facts字段结构、人物参数、时间处理、警告和原断语交付不等价。两边均要求可靠程序盘，不允许模型自行补盘。

本机直接工具主要支持北京时间正时及完整手工四柱，不直接支持活时报数、真太阳时；网站有相应服务端模式。网站高级规则仅接收涉害孟仲季，本机直接工具还列出深度选项。不能把不同模式、默认参数或facts路径当作完全相同的输入。

本轮只核源码、配置和指纹，未执行同盘对照，因而不能证明每个神煞、年命、贵人方向和导出字段在两种适配层中完全等价。

## 六、哪些差异可能影响速度和成功率

有代码依据、值得测量的额外工作：

1. 网站在正式分析前增加独立高推理输入整理，本机由原会话完成该动作。
2. 网站每个新任务建立隔离运行环境，并校验、装载冻结发布资料；本机近期样本按需直接读文件，继续会话可复用上下文。隔离机制应与客户会话复用区分，不能共享客户上下文来提速。
3. 网站有资料分页与覆盖记录、每问完整11环节JSON、事实路径和依赖校验；本机允许把共享节点合并进文字报告。
4. 网站普通报告额外增加最终公开输出规则加载和冻结阶段；本机直接交付完整技术报告。
5. 网站校验失败可能要求修正并再次调用模型，局部检索故障还可能阻止交付；本机规程允许标明部分缺口。

这些机制有部分是权限、账务或证据保护，并非全部应删除。当前没有逐步性能数据证明每项多花多少秒，也没有证据证明6个模块差异是网站慢的直接原因。本机新版内容更多，不能用“网站方法更多”简单解释速度差异。

## 结果边界

本轮已完成当前配置、实际版本、模块正文、检索适配及本机工具记录调查。未运行付费模型、同题同盘基准或新任务，未改变网站和本机的任何执行规则。

需要对齐时，须分别审查：新版应期取数是否迁入网站、逐问JSON是否存在可合并的重复记录、分页与批量读取是否可减少往返，以及公开交付与内部核验怎样保留。上述为后续调查结果的使用方向，不表示已授权或已实施修改。
