## 拒收的具体原因

### 1. branch 字段混入说明文字

第一份输出至少三处不符合程序约定：

- `entity_checks[1].branch`：`申酉（均旬空）`，ID `I_E2`。
- `entity_checks[4].branch`：`卯（官鬼；日支寅见I_E9）`，ID `I_E5`。
- `entity_checks[6].branch`：`戌（末传；干上戌同一天盘支）`，ID `I_E7`。

第二份十个实体的 branch 均不符合当前解析格式。例如 `戊（寄宫巳），干上戌、干阴卯`、`巳（中传）`，还有将多项定位写成整句的情况。

程序在 `tools/liuren-deterministic.mjs:106` 只返回通用错误，没有实体ID、字段路径和原值。`.opencode/plugins/liuren-adjudication.ts:136` 随后用 invalid_output 替换整个 task 返回，主智能体看不到可准确修复的位置。

### 2. 第一份报告还有两项被首个错误遮住的格式问题

仅在离线副本中依次做三项修正，保留原报告与裁决内容：

1. 从以上三个 branch 字段移出括号说明，保留原干支。
2. `special_methods.basis_ids` 中原已有 E01/E05/E17/M_AUTO_TIMING 等有效方法来源，但又混入 D_B0/D_B5/D_B10。当前程序要求此字段全部为方法来源ID，因此仍拒收。离线副本仅从此列表去掉 D_*，未删除原报告或其他依据。
3. 把应期候选从 `special_methods[0].candidates` 移到契约规定的 `special_methods[0].record.candidates`。日期、干支与事件说明保持不变。

这三项改动后，第一份输出通过当前 `finalizeFoundation + validateOutput` 全部校验。证明它存在无需改结论的局部格式修复路径；不证明术理和预测正确。没有将诊断副本写回正式会话或作为已采纳结果。

第二份未做自动归一化验收，其中一项 branch 混合多个对象，不能安全地靠截字猜其本意。

## 为什么重试没有修好

比较三份实际交接包：

- 第一份到第二份：除 request_id 外，只变动 entities；日干戊改为 `戊（寄宫巳）`，申酉组合改为申，相关取用说明相应调整。问题、盘面、事实、观察、书据与争点未变。
- 第二份到第三份：仍只改 request_id 和 entities；`I_E1` 从 `戊（寄宫巳）` 改为 `巳`，referent 仍称“考生/事主（日干戊）”，说明中声称“以巳为日干坐标”。

第二轮没有针对子输出格式修复，而是重做完整裁决。第三份更把日干换成寄宫支，程序计算的对象也随之改变：天干戊的寄宫与天盘巳的落宫不是同一实体。这是为绕过接口错误引入的专业对象偏移，应禁止此类修复方式。

现有错误提示还要求“修复具体缺项后新建裁决”，与工作流中的新会话要求共同把恢复推向重派。缺少“原报告局部修复、重新校验”的路径。

## 与 slim 的状态衔接问题

slim 日志在两次结束时均记录原始 output-v2 报告及 foreground completed，别名分别 liu-1、liu-2。随后本地校验将返回改为 invalid_output。

因此两层状态不同：slim 认为任务已完成、结果待确认；六壬校验认为结果不可交付。第三次派任务被 slim 拦下，明确要求先调用 `task_result` 领取已有结果。截图对应这一错误，不代表第三次裁决已经运行，也不能由错误中的 background 一词推断前两次是后台任务。

主会话实际没有任何 task_result 调用。当前主智能体配置为 `* = deny`，只显式允许 task/liuren-adjudicator，未显式放行 task_result；还须在修复时验证实际工具暴露与权限，而不是只在提示中要求调用。

此外，当前六壬插件仅绑定 task 的请求及返回校验，没有给 task_result 配套同一验收入口。直接开放领取工具仍不完整：必须确保领取原结果不会绕过校验，也不会重新触发裁决。

12:08:47 主智能体尝试原生 read 读取第二份交接文件，被权限拦截。当前 read 白名单没有该 output 路径；这次具体错误不是已证实的旧runtime路径失效。应提供受控交接材料检查路径，不必因此扩大通用文件读取范围。
