# 本机大六壬工作流全链复核

复核基线：`20261106-schema-compat-11`。真实故障会话：`ses_e5116f918ffehcZhxjou41x913`。调查时间线统一采用北京时间2026-11-06。

## 总体判断

“主智能体准备材料 → 独立子智能体裁关键作用 → 主智能体核查并组织报告”的分工可以保留。正常工程通路能够运行，应期与取数能力也没有从程序中删除。但当前失败后的恢复机制不完整，部分工具定义与实际校验规则不一致，必查覆盖、任务范围与原问转写仍主要靠模型自觉。

上一轮确认的“格式失败被转化为整轮重裁”成立。本次扩大核对后，还确认了必查读取缺口、主动扩展应期任务、亲属称谓转写偏差，以及可以不删内容就减少分页的机会。

本轮未改活动文件、冻结包、模型配置或网站/APK；仅新增审查脚本、测试输出与本报告。没有调用真实外部模型，没有创建实际OpenCode裁决任务。

## 需要修复的内容

### 1. 工具参数定义与执行约束不一致

- 原生packet schema将 `questions[].tasks` 标为optional，但当前程序要求必填且非空。离线复现：第一层解析接受，保存时拒绝。
- 原生schema允许 `observations[].verification = chart_checked`，当前程序却拒绝模型写此值。真实本案第一次packet失败就发生在这里；离线复现一致。
- 通用契约的干支检查只要求文本含干支，错误提示还提及“带位置说明的干支”；确定性解析器实际只接受单干支、纯支组合及特定寄宫格式。两套口径容易把模型引向后续拒收。
- 应期候选所在层级及专法basis_ids的类型规则，只靠文字说明；子智能体最终输出并没有原生工具schema约束。因此报告可能语义完整、JSON合法，却在返回阶段才被拒绝。

位置：`.opencode/plugins/liuren-adjudication.ts:27,31`；`tools/liuren-adjudication-contract.mjs:11,54`；`tools/liuren-deterministic.mjs:101-106`。

应统一当前活动版的schema、模板、说明和校验。解释文字不能塞进标识字段，方法来源与盘面事实引用须明确分开。需要兼容旧版时显式按版本处理，不能让当前模型看到两套不同约定。

### 2. 输出拒收后，没有局部修复的正式通路

第一份真实子报告在离线副本中只需修正三类格式就通过全部现有校验：

1. 三个branch值移出括号注释，干支不变。
2. 专法basis_ids中保留实际方法来源，将混入的D_*盘面事实ID移出这个方法来源列表。
3. 将既有候选日期从special_methods成员的candidates移到record.candidates，日期与干支不变。

没有改变原裁决结论。这证明本次存在局部格式修复路径，不证明专业结论正确，也不授权对任何含混branch自动截字。

现状是在第一次错误处立即中止，返回笼统错误，原报告被从主工具返回中替换掉。错误里没有字段路径、实体ID、原值、可修复产物路径；还指示重新派裁决。完整原报告虽能从子会话数据库中找到，却没有成为工作流可用的正式恢复产物。

应先保留原始产物，一次列出可确定的字段错误；可无歧义处理的格式问题只修格式，含混语义才请求有界补正。不得把“输出格式不合”直接升级为重新决定成败或应期。

### 3. 完成、领取、验收和重裁的状态未统一

真实日志显示slim已登记两次foreground completed，而六壬插件随后把输出改成invalid_output。第三次派发时，slim要求先task_result确认已有结果。

当前存在三处缺口：

- 主智能体 `* = deny`，未显式允许task_result；本案也没有调用过task_result。当前权限的实际工具暴露仍需在修复后的宿主集成验收中确认，不能只补提示词。
- 六壬插件只绑定task；离线探针把同一份无效JSON作为task_result返回，插件原样放过，没有六壬验收元数据。因此仅放开领取权限仍不够。
- “同材料不重裁、最多一次具体补核”的约束未在六壬程序中落地。相同packet连续三次都能通过六壬before钩子；slim的去重是另一层机制，不能代替本工作流自己的重试预算。

pending、authorized与读页记录都在进程内。重新实例化插件后，旧文件的读取授权不能恢复。这是恢复能力边界，不能用无限放宽文件读取权限补救。

应对request_id、父子会话、材料hash、原始结果、验收结果与重试原因建立同一份可恢复记录。领取已有结果不应触发新推理；task与task_result必须进入相同校验。已产出、已领取、已通过和已交付应是不同状态。

### 4. 必查读取与实际派发之间缺少核对

活动reading-route列14项共同必查。本案主智能体读取了其中13项，没有 `engine-shensha-output` 完整模块读取记录；其他工具返回里也未发现该模块的完整正文。只看到Skill和其他模块提及其ID，不能据此视为完整读取。

这不直接证明神煞起法或取用已经判断错误。程序神煞采用层本身仍在工作；缺的是明文流程要求与真实读取覆盖的对应证据。

离线探针也确认：不提供任何主智能体方法读取回执，六壬task仍能派出。现有before钩子核文件、父会话和配置，不核本问必查覆盖。

建议用已有method返回的module、fileSha256和完整返回信息做轻量核对；同版同上下文真实已读可以复用，不增加模型调用，不强迫重新prepare或再读一遍全书。该检查只能核材料取得，不能宣称模型理解和运用正确。

### 5. 原问范围与应期任务的来源没有区分

原用户只问转校入学考试“能否进去”，给了占时，没有另问何时录取。交接包却声明tasks为outcome+timing，因此自动装入完整应期方法，又产生日期计算和完整special_methods输出义务。

本案17次资料调用实际为16次不同方法读取、1次book_search；15次source调用主要在装配连续书据。不能将本次延迟概括成“疯狂检索书籍”。

应期是用户此前明确重视的能力，不能为省时一律删除。但应区分原问必需、用户明确要求与分析附带补充。若只是附带时间提示、实际考试节点又未知，应有明确的适用条件与精度范围，不能无说明地扩大成强制精细日期任务。数量任务同理。

程序能校验已声明任务的覆盖，不能从自由文本自动保证模型声明的tasks完整且必要。目前这一选择仍由主模型作出。

### 6. 原始事实保留了，规范化转写仍有偏差

原问是“姐姐的女儿”，交接subject及实体说明却称“侄女”，准确称谓应为外甥女。原始题干在facts中仍正确保留，时间也与程序盘2024-01-15 15:23一致，未发现把工具示例日期当本案日期的问题。

亲属称谓错误是否影响本案六亲取用，须另按专业规则判断，不能在本次工程复核中直接断言。但它说明原文被保存不代表派生角色标签就不会错。

应将“用户明示关系”与“术数取用角色”分开，对两者冲突作提示；禁止为修字段把日干换成寄宫支。本案第三包确有将戊改成巳的问题，详见上一份日志诊断。

### 7. 存在不删专业内容就能减少读取次数的机会

第一包按现有格式为101,427字符、11页；同一JSON数据紧凑序列化后为55,788字符、6页。其余两包结论相同。差异来自缩进和换行等格式空白，未删盘面、书据、观察或专法。

紧凑存储可以作为优化候选，须重新生成hash、保留完整读页校验并验证不截断。不能原地改写既有交接文件。此处只计算字符和页数，没有实际测出模型token或端到端耗时下降比例，不能承诺时间减半。

首先避免整轮重裁，收益通常比压缩单页更直接；随后处理来源装配返工与分页。是否进一步合页，应按宿主实际返回预算验收，不能靠删材料达成。

### 8. 最终报告一致性仍是模型规程，不能宣称已被宿主强制保证

report模块明确要求主智能体复用裁决结论、理由、条件、精度，不重新权衡；这一分工与用户接受的方向一致，无须删除主智能体的前置理气准备。

但本案尚无通过验收后的完整最终报告，所以不能证明这一步真实运行已合格。程序能核ID、字段、日期、算式，不能仅凭这些保证自然语言报告没有增添新理由或改变事件层级。

后续验收须保留已采纳结果ID及版本，对最终报告逐问检查：结论是否一致、条件是否保留、应期/取数是否完整解释、是否新增决定性理由。未知项是否属于必要缺项也仍需专业判断；不应将所有unknowns机械变成needs_input。

## 已确认保持正常的部分

- 当前裁决模型为DeepSeek Flash，variant及reasoningEffort均为high；项目配置prompt与同版文件完全一致。
- 正常文件交接、完整页读取、父子绑定、文件hash校验可以通过；真实两位裁决者各读1到11页，没有同一位无故重复读同一页的证据。
- 应期与数量源文仍自动装入；11项探针包含三任务共存、应期日期核验和金额不符拒绝。它们没有从接口中被取消。
- 主子边界、经验库/案例库禁用和大六壬占事范围维持。没有证据支持为本次故障撤销整个独立裁决架构。
- doctor确认当前运行包、神煞版本和程序排盘正常；其总体ok仍为false，原因为既有研究库85条登记问题。本轮未逐条复审这些问题，也不把它们归因于本次重复派裁决。

## 建议修复顺序

1. **先打通结果接收与恢复**：原报告留存、结构化错误、局部修复、统一task/task_result验收、可恢复状态与重试预算。
2. **统一输入输出约定**：tasks、verification、branch、引用类型、应期/数量模板；避免第一层允许、下一层拒绝。
3. **补前置对照**：原问与规范化事实、任务来源、必查读取覆盖；复用已取得材料，不重跑全流程。
4. **再做无损减负**：紧凑交接、减少来源装配重复和分页；保持专业能力及必要证据。
5. **验收三类路径**：正常完成；已有报告格式失败后局部恢复；真实缺材料/事实错误后一次有据补核。最后检查完整中文报告是否忠实承接裁决，不能只以131项基础测试通过宣布整链完成。
