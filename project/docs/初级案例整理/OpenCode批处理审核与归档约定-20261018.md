## 归档完成条件

单案归档使用原`liuren-cases`的R1—R4流程，同时加载`liuren-extract`检查经验来源、META、AI补充标识和未验证边界。两者均由当前DeepSeek主模型执行；固定文件与索引操作由脚本完成。

1. 案例保留源编号、源文件、盘面路径、初判摘要/原文链接、实际反馈、逐问判验与复盘；AI分析与原材料中的人类作答不得混淆。
2. 案例失准也留档，失准不得被反推后的答案覆盖。缺反馈写未载，反馈为优秀作业的材料不得伪装实际结果。
3. 疑似经验逐条写明：现存依据、疑似链条、推断环节、反证/其他解释、适用边界、待验证问题。
4. 单例反推条目标`经验状态=未验证从疑`，经验自身的`反馈=未载`，独立验证次数为0；现实事件的明确反馈另行记录。不得给旧经验增加验证次数、修改权重或把候选当已验证裁决依据。
5. 无法预先说明选择规则的事后组合只可留作假说。没有合理依据的猜测不必凑成经验；记录无可采纳新增也算完成。
6. 执行来源去重、分配案例编号、双库写入、案例索引增量更新、原脚本重建经验索引、读回核验，并保存归档回执；不能只输出“已归档”。

归档脚本：`tools/archive-opencode-case.py`。已扩展到用户授权批次：新案须有Codex逐案审核记录及初判/复盘文件哈希，全部同批分析完成后才能写入。支持归档回执重复核验，拒绝覆盖目标文件，共享写锁避免同时分配编号/修改索引。无可靠新增经验时，经验文件只留待反馈记录，不强制生成规则。

## Token与费用边界

并行通常主要改变耗时，不会自动减少每案token。独立会话重复加载规则、重试与审核会增加消耗；缓存命中可降低部分重复输入的费用，但不能把累计缓存token当作新增内容量。

审核先看原始问题、必要盘面、初判、反馈、复盘与疑似经验，疑点才追读具体原文；不把全部skill、历史索引和事件日志再交给审核模型重读。保留完整规则与可追溯资料，不通过删减原skill省token。
