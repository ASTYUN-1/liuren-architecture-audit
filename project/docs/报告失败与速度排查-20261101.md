# 问衡报告失败与速度排查

## 结论

今天失败的直接原因是网站单轮600秒硬超时，且超时后没有续跑，自动从头重做，连续三轮超时后才宣布失败。另有10月31日的单次模型输出达到32768 token上限，触发输出不完整错误。现有审计没有显示这些故障由余额不足、429限流或工具次数耗尽造成。

速度慢有三层：工作流本身需要多轮模型生成和工具操作；600秒超时后整轮重做进一步放大耗时；单worker串行执行使同时提交的任务排队。页面刷新不是上述生成失败的直接原因。

## 建议修复顺序

1. 优先修复超时后的整轮重做：补可恢复检查点或保留受限会话状态；区分网络暂时失败与工作流总时限耗尽。结合实测调整有界时限，同时协调pg-boss过期时间、取消与心跳、费用上限，避免仅把10分钟改长后继续三轮重做。
2. 处理单次输出长度耗尽：记录finish_reason及安全用量指标，采用分步提交/分块判断与受控续写，保证工具参数完整；核实供应商能力后再决定是否调整token上限。保留完整方法与证据核验，不删除skill换速度，不将截断内容标为完整报告。
3. 补脱敏性能轨迹：记录请求起止、耗时、finish_reason、工具名及安全错误码、读取覆盖和最终提交阶段，接入真实进度；不保存密钥、客户原文或原始思考过程。这样才能验证是否存在重复读取或反复校验，并针对实际热点减少往返。
4. 在隔离环境核对权限、计费幂等、取消和恢复后，以有界小并发测试改善排队。增加并发改善多人等待，不能使单个任务的推理时间自动变短，也不能未经测量盲目提高并发。
5. 修复后用固定盘、同题同版本比较网站与本地链路，分别验证主报告/追问、专业/通俗、超时恢复、输出长度和两任务同时提交；完成真实生成验收前不宣称问题已修复。
