风险 01 · 最硬的一块

八字算的是「真太阳时」，不是钟表时间

这不是小修小补。用钟表时排盘，同一个人在北京出生和在乌市出生，时辰可能差两小时——四柱全变。海外更极端：15 个美国时区 + 历史夏令时 + 国际日期变更线。引擎现在只认中文城市码，这一层不做，后面全是错的。

校正公式

真太阳时 = 钟表时
+ (当地经度 − 时区中央经线) × 4 分钟/度
− 均时差 (全年 −14.2 ~ +16.4 分)
中央经线：UTC+8 → 120°E · UTC+0 → 0° · UTC−5 → 75°W

同一钟表时刻，校正量能差多远

伦敦 · 0.1°W
≈ 0 分
纽约 · 74°W
≈ −12 分
北京 · 116.4°E
≈ −14 分
乌鲁木齐 · 87.6°E
−2h10m
乌鲁木齐那一条不是极端个例，是国内同一制度下的真实断层。海外用户横跨十几个时区，量级只会更大。

要做的四件事

  • 地理编码：用户输入城市名 / 邮编 → 经纬度。建 city_geo 缓存表，别每次调 geocode API。
  • 历史时区 + 夏令时：必须用 IANA tz database 查出生那一刻的 UTC offset，不能用今天 的。1985 年前美国还有 DST 变化，规则改过多次。
  • 月份归属：月柱按节气分月，年柱按立春分年，不是公历 1 月 1 日。跨年出生（1 月 1–5 日）极易算错年柱。
  • 时辰边界必须提示：校正后若距时辰分界 < 10 分钟，给出两盘并列（前一刻/后一刻）让用户选，不要假装确定。这是专业度的体现，也是防投诉。

打分函数

score = 0.40·vector_sim
    + 0.25·exact_field_match // 日主/月令/格局 全中
    + 0.20·min(log₁₀(1+验证次数), 1.5) // 已验证次数
    + 0.15·source_authority // L0 古籍 > L1 技法 > L2 命例
    − 0.50·no_source_penalty // 无 来源 字段直接出局
最后两项就是「反推纪律」第 1、3 条的数学表达：没有出处的条目不得进入推理；验证次数是单调递增的加分项，不能靠「写得像真的」上位。
反馈闭环

反馈不只是补偿金，是知识库的供给管道

你项目里的 命例-实战反馈.md 已经是这个闭环的原型：预测 → 反馈 → ✅/❌ → 技法提炼 → 验证次数 → 反例边界 → 来源。产品化要做的，是把这条人工链路变成自动流水线，并加上付费激励和防投毒闸门。

④ 到 ⑥ 之间可能相隔数周甚至数月——这是对的。「未验证从疑」的条目在等待期里不参与主力推理，只在同类命例提示里以弱证据露脸。急不得，这一步走快了整套体系就被污染了。

七道防投毒闸门

  • 表单结构化：强制填「哪条预测（从报告里勾选）+ 实际发生什么 + 时间」，不给自由文本空间。投毒需要自由度，结构化本身就是收敛。
  • 可证伪性检查：「我 2027 年会发财」这种不可证伪的，直接判退。
  • 与已有条目冲突检测：新反馈若与 L0/L1 已验证结论矛盾，不覆盖、只并存标记。
  • 「未验证从疑」标签：反推纪律第 3 条，你已经写好了。
  • 验证次数 ≥2 且信源独立：同一支付卡 / 同一 IP 的多条反馈计为 1 次。
  • append-only + 来源可追溯：条目永不删除、永不覆盖，只能追加修订记录。
  • 奖励预算月度上限：运营层兜底，防止被刷出真实资金损失。

返现 / 优惠：发 credit 而不是退钱

状态机
submitted → auto_reviewed → approved / rejected → reward_issued
默认奖励
下次消费抵扣 50% credit（有效 90 天）
可选升级
用户可主动选现金退款（走支付方部分退款 API）

按订单额计算，设上限（如 ≤ 40% 订单额）

为什么默认给 credit：现金退款会触发支付争议/拒付，长期亏损率通常高于奖励金额；而且现金退出会把用户送走，credit 会把人留下来复购。给「退钱选项」但做成用户主动升级，既满足「我们给你返一部分服务费」的说法，又把默认路径留在你这边。

合规红线

四条不能碰的线

1 · 免责声明要够、要在付费前

结账页 + 报告页 + 报告 PDF 三处都要有。不构成医疗、法律、财务建议。这句话不是形式主义——它是海外消费者保护诉讼里最有效的抗辩点。

2 · 禁止输出「绝对断言」

在 LLM 的输出约束里加死规则：不许说「你一定会」「你 100% 会」。用「倾向 / 容易 / 在 X 条件下」。既是合规，也是防止用户事后扯皮退款。你已有的「从疑」体系天然支持这种表述。

3 · 健康与财务要降级

「你 3 年后可能有一次健康波动」可以；「你该去做 CT」不行。所有「建议就医/投资/离婚」的输出直接过滤掉。这条做在状态机输出 schema 层，不靠 prompt。

4 · PII 与 GDPR

出生日期时间地点是高度敏感的个人数据。Supabase 选 EU region，报告默认 90 天自动删除，导入口径 + 隐私政策要齐。面向欧盟用户时不这么做会直接吃 GDPR 罚单。

另：Google Ads / Meta 对占卜类广告有限制，投放计划要预留。获客建议先走 SEO + 内容（八字/五行英文长尾内容竞争度低），跑通再投广告。

三件需要你先拍板的事

决定架构

收款主体在哪？大陆主体走 Stripe 很麻烦，MoR 平台反而更顺。这决定支付层选型，也决定要不要 MoR。

决定范围

先做八字还是六壬？八字一次性付费、链路短、好验证；六壬高频但推理重 4–8 倍、还要处理「用户随时起课」的实时性。建议先八字。

决定形态

先做英文单语还是 EN+ES+PT？建议首版纯英文跑通验证，翻译层架构留好口子，第二语言后面加就是配置工作。

这三个答案不影响第一阶段（WEEK 1–2 的引擎服务化 + 时区校正）怎么做——那部分无论怎么选都要做。可以边做边定。
