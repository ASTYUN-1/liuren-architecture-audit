# 网站与本机速度对照核查

2026-11-01北京时间23:46左右补查生产任务技术元数据；本轮未修改配置、重启服务、重跑客户任务或调用付费模型。用户反馈本机完整输出约4—5分钟，该耗时尚未绑定到一个可复现的同题对照样本。

## 已确认结论

网站旧执行机制确实有工程缺陷，曾主动放大等待时间，并非所有长等待都来自问题复杂或API供应商速度。原10分钟总限触发后从头重做、最多3轮；原单任务执行还会引入排队。这两项已在21:34发布时处理，但本次查询未发现该发布后新建的生产任务，因此尚无新版本真实生成耗时可作验收。

## 本机与网站的差异

只读核查本机两个相关项目的OpenCode消息元数据，实际记录中存在大量`deepseek/deepseek-flash`、`orchestrator`调用；不能因当前全局默认模型为其他模型，就声称用户本机一直使用不同模型。网站当前固定`deepseek-flash`、高推理强度；具体那份4—5分钟本机报告的模型参数尚未确认。

网站采用受限MCP、8000字节资料分页、13个必读基础模块、逐问十一环节记录、结构校验及最终输出阶段；本机使用直接文件/工具与本机报告规则，不能视为相同执行路径。网站每项任务独立新建OpenCode进程和会话、结束清理，不复用上一任务的已读上下文。任务隔离应保留，可评估安全的静态资源缓存和独立工具批量读取，不能共享客户会话。

这些差异提供优化方向，但仅凭代码不能证明每项开销具体是多少。多次模型与工具往返形成真实耗时；单轮成功记录已经能达4分46秒，说明不能笼统认定公网一律比本机慢很多。

## 目前不能证明的事

- 历史记录没有逐次模型请求开始时间、每个工具耗时/错误轨迹，无法准确将几分钟分摊为推理、工具、重复读取或校验修正。
- API用量事件只有完成时间；相邻完成时间差包含模型、工具及调度，不能当作某个API请求精确耗时。本轮统计的中位间隔约3—12秒、最大间隔约48—179秒，不证明工具被限频。
- 非流式会推迟可见输出、阻碍识别进展，不能直接断言改成流式就会大幅缩短完整报告生成时间。
- 单次主机资源快照和API入口连通，不足以证明历史生成期间网络与供应商从未变慢。
- 尚未完成同题、同固定盘、同资料版本、同模型参数、冷会话对照。不能承诺改后所有报告4—5分钟完成。
