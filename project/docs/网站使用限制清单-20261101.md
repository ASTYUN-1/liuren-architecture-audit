## 一、为什么还有单次5分钟

网站在 `src/agent/execution-control.ts` 定义 `MODEL_REQUEST_TIMEOUT_MS=5*60_000`，在 `src/agent/gateway.ts` 的上游fetch中通过 `AbortSignal.timeout` 执行。它是网站自己设置的等待上限，没有证据表明API供应商要求必须设成5分钟。

设置请求超时通常是为了避免断网、上游无响应等情况长期占用执行位置和资源。但没有查到“为什么恰好取5分钟”的性能验收依据，不能把这个数说成已经验证的最佳值。

目前请求强制采用非流式返回，并启用较高推理强度。完整响应回来之前，网站看不到逐步生成进展，因而无法可靠区分正常长思考、供应商排队和真正卡死。复杂任务也可能被5分钟限制中断。网站停止等待，也不保证供应商立即停止计算或计费。

30分钟是外层整项执行上限，不会覆盖内层90秒、5分钟、15秒等限制。只把整项上限延长到30分钟，尚未解决复杂单次推理被提前中断的问题。

## 二、直接影响报告生成的限制

| 环节 | 当前规则 | 实际影响 |
| --- | --- | --- |
| 正式分析前的输入整理 | 单次90秒；非流式；输出最多8192 token | 这一层失败时，正式解读尚未开始，用户可能已经觉得“不能生成”；不扣报告积分 |
| 单次正式模型请求 | 5分钟 | 整项任务即使未到30分钟，单次等待过久仍可能失败 |
| 整项分析 | 从实际执行开始最多30分钟 | 不包括排队；不是保证30分钟内必定交付 |
| 无有效进展 | 连续6分钟 | 成功模型响应或成功工具调用才计进展，普通心跳不算；仍可能误判极慢的正常推理 |
| 单次MCP工具调用 | 15秒 | 工具异常或过慢可以先于总上限失败；固定资料检索另有子进程10秒边界 |
| 重复错误 | 同一工具连续5次同类错误停止 | 防止反复无效调用；这不是对问题复杂程度的识别 |
| 调用数量 | 每轮模型请求最多200次、工具调用最多200次；OpenCode步骤同样有界 | 达到次数后不能继续；不是每个用户每天200次 |
| 单次模型输出 | 最多32768 token | 长输出可能截断，token不等于中文字数 |
| 输出截断恢复 | 在原会话恢复一次 | 保留已读资料；再次截断仍可能失败，不无限续写 |
| 最终报告字段 | 正文200—16000字符、摘要20—600字符、标题2—100字符；内部引文3—12条 | 即使模型还能输出，也必须满足交付格式和内容校验；追问交付正文同样最多16000字符 |
| 子问题登记 | 最多20个 | 不支持无限扩展子问题 |
| 队列工作过期 | 发送任务时显式设置35分钟 | 是后台工作保护，不是排队等待承诺。数据库队列模板仍显示20分钟默认，不能据此误说本次任务实际20分钟必停 |

报告还必须通过规定流程、固定盘、资料读取、引文等校验。模型写出一段话，不等于网站允许交付。修正不合格输出会增加模型往返和工具调用次数；校验通过也不证明所有术理判断正确。

确定性的超时、停滞和错误循环不再整轮自动重做。有实际工具执行或多次模型请求后，也不会丢掉整轮工作重跑；仅尚未实质执行的暂时故障保留有界重试，最多3次尝试。尚未实现服务重启、进程崩溃后从持久检查点继续同一分析。

## 三、并发、排队、取消与保留

| 项目 | 当前限制 | 说明 |
| --- | --- | --- |
| 全站报告并发 | 同时2项 | 第3项开始等待；可配置1—4，不代表现有硬件和供应商已验收4并发 |
| 工具能否并发 | 不同任务的模型、MCP工具可同时工作 | 此前通过隔离工程验证；不是后台技术做不到并发。提高并发主要减少多人排队，不自动缩短单次推理 |
| 同一档案 | 同时仅1个排队或执行任务 | 避免主报告与追问、多个追问的盘面、状态及扣费冲突；未见整个账号只能运行1项的统一限制 |
| 补充资料 | 最多恢复2轮 | 原任务超过7天或已取消，不能继续旧补充流程 |
| 追问时机 | 主报告完成后 | 当前积分模式没有统一的“每档最多8次追问”；8次是旧套餐限制 |
| 运行中取消 | 滚动24小时内按取消审计累计3次后拒绝新的运行中取消 | 当前统计包含排队取消、删除档案触发的同类取消，口径比“只数运行中取消”更宽 |
| 排队取消 | 不单独检查上述3次门槛 | 仍会留下同类取消审计，且受积分操作接口频率限制 |
| 未完成任务 | 创建超过7天自动取消 | 包括排队、运行、失败、等待补充；正常已交付报告不取消。保留历史，释放未结算权益 |
| 删除档案 | 回收站保留7天 | 主动永久删除后不能恢复；进行中的特定真人服务须先处理 |

7天是清理长期未完成记录的期限，不是允许单次模型连续运行7天。维护循环及队列消费还会带来秒级调度延迟，目前没有固定排队时长承诺或已验收的大规模公平调度能力。

来源：`src/server/worker.ts`、`service.ts`、`points-ai.ts`、`point-task-cancellation.ts`及本日发布记录。

| --- | --- | --- |
| 新问题/追问的起课意图整理 | 6次/60秒、40次/24小时窗口 | 每账号；两个整理接口共用。不是每天最多完成40份报告 |

| 积分操作 | 60次/小时 | 每账号；AI任务、取消、退款、真人预约等POST共用 |
| 更正起课输入 | 10次/小时 | 每账号 |
| 免费排盘 | 10次/分钟、100次/24小时窗口 | 按识别到的来源计数；IPv6按/64；共享出口可能共用，不能称每人独享100次 |

## 六、账户权限、积分、通知和真人服务

### 账户与权限

- AI需要登录。普通账号可以使用用户名注册，不是一律必须绑定并验证邮箱后才能解读。
- 登录账号4—24位小写字母、数字或下划线，保留名拒绝，设置后不能随意改；昵称1—40字符；自定义注册密码10—128字符。
- 登录会话有效期7天并按24小时周期滚动续期，不是每7天必定退出。
- 卦师专业输出需已验证邮箱及相应认证或官方绑定；普通卦师认证不等于获得任意客户档案阅读权。
- 管理操作需要管理员身份及已验证邮箱。此次实查`ADMIN_REQUIRE_2FA=false`，当前不强制运营者开启两步验证，不能沿用旧文档相反结论。
- 管理员及已启用两步验证的账号不能使用普通恢复密钥找回路径。没有有效恢复凭据或已验证真实邮箱，会影响找回。
- 保留同源和CSRF校验；第三方页面直接调用写接口可能被拒绝。验证码是否在线启用未核实，不能断言已开启。

### 积分与费用

- 主报告基础费用30积分，通常先预存100积分；符合8折券时预存80积分。追问基础费用5积分，不预存，但开始及执行前需有最低可用积分且没有欠费。
- 成功交付按实际API用量及既定加价/折扣结算，1元=10积分。当前计量模式下，100积分不是单报告最终费用上限；超过余额的交付可记欠费，补足前不能开新任务。
- 当前没有查到独立的“每任务最多花多少钱”硬预算中断机制。时间、次数和输出上限只能形成间接费用边界。
- 未交付/失败释放网站未结算积分，不代表上游已发生的API调用必然免费。
- 成功结算发现无法核验的用量记录时，会自动关闭全站积分AI开关，等待运营核查。这是账务保护，也可能导致用户暂时不能开始解读。
- 当前充值、AI、真人开关开启，公众聚合支付开关关闭。供应商API余额与用户网站积分是两套账；现金退款还需实际核对，不能将网站退积分等同于现金到账。

### 通知、运营角标和展示

- 验证链接1小时有效；验证/找回邮件同收件人5次/小时，服务类20次/小时。
- 邮件全站每日最多100次发送尝试，失败也计数。按UTC日期切分，对应北京时间08:00换日，不是北京时间零点。第三方接受发信不等于收件箱实际送达。
- 主报告结果有邮件通知流程；追问完成、澄清和失败通知按现有节省额度策略抑制，需到原档案查看。未绑定有效已验证邮箱，也不能依赖邮件提醒。
- 报告整体提交及校验后展示，不逐字输出。分析页约6秒轮询；页面隐藏暂停前端轮询，重新聚焦恢复。关闭页面不会主动取消已入库的后台任务。
- 进度百分比是估计，交付前不会真正达到100%，不能将它当作已完成工作的精确比例。
- 运营通知约15秒刷新；只有进入对应模块且可见约2秒才将展示消息标记已读，也可手动标记。读过不等于审批完成，未读数不等于全部待办数。
- 语音依赖浏览器能力、权限和网络。旧APK内置界面未随本次网页发布重新打包，新角标不能保证出现在旧App界面；后台任务策略同站。

### 真人服务与分享

- 当前真人服务150积分/10分钟，先有AI报告，且接待开放并具备有效联系/阅读账号。
- 待接单默认24小时；接受后再24小时；交付后48小时无异议自动结算；争议窗口7天；其他到期未完成按流程释放积分。
- 分享通常7天，可明确续授权；仅指定合作卦师及有效分享凭据可读，撤销或过期后不可继续读。

## 七、公网入口、机器与外部限制

香港Nginx两个当前入口均有来源地址限流：API平均10次/秒，允许20次突发，超过可返回429。来源地址可信传递和共享出口会影响是否多人共用，不应默认每个真实用户独立计数。

入口普通代理读取等待120秒，请求体最多2MB，读取请求头10秒、请求体15秒、发送30秒，连接保活30秒。这些主要约束单次网页HTTP请求，不等于后台报告只能跑120秒；报告已入库后由worker异步执行。常规业务JSON还有应用层更小的32KiB限制。

业务、数据库和AI worker在旧电脑Ubuntu，香港VPS提供当前公网入口。检查时业务主机内存约5.9GB、可用约4.6GB、无swap，磁盘可用约16GB；属于当时快照，不是永远可用资源承诺。旧电脑、网络、转发、数据库、供应商任一环节故障都可能影响网站。本机正常并不能证明这条公网链路同样正常。

当前没有证据证明服务器资源已经是本次报告失败的直接原因。提高并发后仍需真实负载和真实模型验收，不能仅看可配置到4就宣称可稳定承载4。

尚未登录供应商后台核实其真实限频、并发、日/月额度、上下文和拥堵情况；Cloudflare账户级额外规则也未完整核验。有API余额不排除上游429、拥堵、响应不完整或网络故障，但不能把这些未经证实的情况当作今天故障的结论。

## 八、优先处理建议（本轮未实施）

1. 协调90秒输入整理、5分钟单次请求、6分钟无进展和30分钟总限。只放开其中一项，其他项仍可能先中断。
2. 改造为可观察有效进展的模型通信，并区分请求尚未响应、工具失败、循环、整体超时；正常连接心跳不能直接算分析进展。不需要公开模型内部思考。
3. 复核每账号40次/24小时的输入整理额度，以及失败重试计入额度是否符合实际使用。
4. 增加可恢复的任务阶段与持久检查点，再做排队公平性和真实并发压测。
5. 明确每任务消费预算与用户可见价格边界，避免将预存额理解为封顶价。
