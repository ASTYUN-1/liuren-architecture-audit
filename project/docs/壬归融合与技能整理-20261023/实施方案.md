## 2. 已确定的设计决策

1. 北海三步法继续作为统一判断主干，不增加与其竞争的“壬归总流程”。
2. 日辰关系归入课传结构及对象关系，类神归入对象定位；二者须连贯使用，不硬选一方后屏蔽另一方。

4. 主入口、共享判断方法、占类专项、来源与历史材料分层；一条当前执行规则只有一个维护来源。

6. 常规占事由一个主入口负责；旧方法 Skill 的运行内容整合成模块，保留旧名称到新模块的映射。
7. 当前要求核查的八煞九宝与32项神煞完整保留。起法/位置能确定计算的部分可工具化，作用有效性由判断者核对。
8. 不通过缩写原材料绕过输出上限。原始材料保留完整快照；新执行文本允许无损归并，但每条条件、例外与方法差异必须可追溯。
9. 新版采用逐问判断记录；资料读完、格式合格、推理成立、结果命中分别验收。
10. 首次实现使用现有语言与运行工具：Python 维护/构建、TypeScript 网站适配。无需引入向量数据库、额外框架或自动多代理系统。

## 3. 统一判断核心的具体内容

### 3.1 北海三步法的执行产出

| 主干 | 具体动作 | 必须留下的可核对摘要 |
|---|---|---|
| 明占类 | 保存原问；拆对象、事件、阶段、时间范围与成功标准；分出结果、程度、属性、身份、地点、数量、时间 | 本题究竟判断什么，哪些已知、哪些待判断 |
| 定侧重 | 按占题固定日干、日支、类神、相关年命的角色；核取用来源；选择直接回答该问的关系 | 一条主线、取用依据及必要的竞争解释 |
| 看显象 | 检查关键节点位置、月令五气、临地/十二气、神将、生克脱耗、刑冲合害空墓、直接阴神 | 关系存在与作用有效分开，说明作用于谁、影响哪项结果 |
| 看显象中的动态深化 | 检查发用、用传、相关年命的引动、转折和救制 | 初判在哪一条件下成立或改变 |
| 收束 | 比较最强反证，分别裁决结果、过程、程度；涉及时间再取应期 | 结论、边界、依据依赖及未定项 |

主线不能只写“类神线”“三传退茹”“水势”。应写成“本对象通过哪一种盘面关系与本问结果相联”。这是工程上的执行要求，不伪称《壬归》原文逐字规定了该格式。

### 3.2 《壬归》融合点

- **四课与日辰对待**：检查主体、对象或双方的状态与相互关系。角色随占题确定，不全局固定“日干永远是问话者、日支永远是宅”。代问须说明当事人与问者的分工。
- **类神与乘临**：分别回答类是否存在/显现、是否得气得地、能否被本人取得或影响本人。未入通常课传仍有按类检查的路径。
- **五气、十二气与六亲**：分别记录月令参照、长生参照对象与临地、相对于谁取六亲；不能相互替代。
- **用传**：说明发端、转移、归宿或本占类规定的角色功能。不要将所有三传机械解释成过去现在未来，也不预设三传只能讲过程而不能影响结果。
- **阴神**：从已明确的对象及坐标取其直接阴神，查扶损、限制、后续作用；继续追溯须说明新增一层解决什么疑问，重复或无新增关系则止。
- **制救**：逐一指出所救对象、被制对象、作用关系、双方状态、受限条件与解除范围。解除关键阻碍后重新裁决；局部缓解不扩大为全局成功。
- **天官及八煞**：结合神将状态与具体关系解释；不得把吉凶名称直接等同于结果。区分《壬归》自身八煞口径与其他书的八煞九宝名单。
- **先锋**：保留占时察端倪的相应用法，不成为每个明确占题的最终否决权。
- **类神三传**：保留来源、取法及用途，作为明确需要追索该类始终时的专项方法；与通常发用所得三传分列，不强迫每题重复展开。

### 3.3 主次裁决

不设“课体/类神/天将/理气永久排名”，不按吉凶条目数量投票。每个关键依据依次检查：

1. 是否针对同一对象、事件、阶段和判断标准？
2. 取用、坐标与作用关系是否有据？
3. 相关方法的条件是否成立，施受双方是否有效？
4. 它决定结果，还是影响过程、程度、时机？
5. 最强相反依据是否被具体解释？不能裁决时保留未定与条件分支。

“充分/必要条件”的措辞只在相应方法确有依据时使用，不把任何传统断语擅自形式化成逻辑定理。

### 3.4 车库复盘怎样用

仅把用户给出的片段作为已曝光的开发反例：角色被命名，却未进入主判；“无大灾”与“完全不进水”混淆。完整课盘、原始问答、反馈时序未取得前，不补造古课字段，不宣称已重新验证结论。

以下只能作为待审推断，不能纳入通用规则：水未临支便绝不进水、支上火必然干燥、辰为水库便是空库、三传空便绝无局部影响。反过来也不能将“单项不足以证明”改写为“该象永远无效”。

`core.md` 必须包含足以完成一般判断的连贯方法，不能只是索引。复杂机制放专题；核心仍须说明何时触发、为何需要、读完怎样回到当前问项。可保留少量成对示例帮助理解条件边界，不用全部历史案例挤占每次上下文。

目录按职责组织，不按新增一本书就新增一个总 Skill。原文与历史全文存入不可变 baseline 或来源资产，通过明确链接查阅，不混成当前执行口令。

### 4.1 候选本地入口

构建器在每个候选包内生成 `.opencode/skills/daliuren/SKILL.md` 和它自包含的 `refs/`。常规占事只从此入口进入，按本题读取成组模块。

迁移期间不删除活动工作区任何旧 Skill。案例检索、提取、终身推命继续由原有入口承担；候选测试范围限定单事判断。候选内若保留这些任务入口，必须同时带齐其相对引用闭包并验证，不能把其依赖留成断链。

旧的八方法名字保留在 `legacyAliases` 映射中，便于查证与网站兼容；候选常规流程不再把它们列成八次独立必调。不要为每个模块另外生成一个自动触发的 Skill。

### 4.2 加载规则

第一批：core、evidence、本问所需占类专项、完整断课必查的shensha基础模块及其他明确触发的机制；一次注册所需模块，工具按安全分页上限批量送达。纯排盘、资料查询不强行进入完整断课。

第二批：针对尚未解决的争点，增读对应完整机制或源文小节。每次增读说明解决哪个问项/争点；已完整读取的同版本模块复用。

第三批：核对决定性原文、最强反证与案例差异，按结论依赖重评。

所有正式断课保留八煞九宝与32项的基础核查要求；无关项目可记已核但不采用，不要求逐项扩写。程序可以提供核查结果及出处索引，但不自行裁定神煞对具体人事的效果。

跨源的空亡、十二长生、内外战、土寄生等口径保留分支，选定的来源与参数进入判断记录。禁止为追求统一文本而合成一个无人提出过的新通则。

### 4.3 体积与跳转原则

不设置必须压到某字数的硬目标。先保证条件、例外和区别完整，再删除重复与移出非必需历史材料。原则上“入口 → 完整模块 → 必要源段”足够；有实际理由可以继续，不能为了限制跳数省略必要核对。

维护层与交付层分开：构建器按确定的源段组装，不用 LLM 临时摘要。不得把合并文件当作规避8KB分页的办法。计量记录 unique source bytes、delivered bytes、重复字节、工具次数、实际模型token（可得时）、耗时；这些指标不替代准确性。

| zhinan-zhanbing | domains/classical-conflict.md | 原古典兵占边界，不外推为普通人际通法 |
| liuren-cases | evidence＋保留原任务入口 | 真实检索、问题匹配、原案/反馈身份与同源去重 |
| liuren-extract | 保留维护任务入口 | 反推纪律、候选身份、来源、归档边界 |
| liuren-tuiming | 保留独立原入口 | 当前推命方法与依赖，本轮不改其理论 |

八字三项不参与迁移。出行、天时、家宅等缺独立专项时，沿 core＋有据源文读取；不得为了凑齐目录临时编造一个已成熟专项。

迁移表必须细化到段落/规则级：`sourcePath/sourceHash/section/oldTextHash/targetModule/action/reason/sourceIdentity`。action 至少区分 `retained`、`merged-equivalent`、`historical-reference`、`conditionalized`、`unresolved`。不能把整本标为已迁移就宣称无损。

`conditionalized` 表示实质规则表述变动，只进入 enhanced；structural 保持当前执行含义。历史原文即使有“必”字仍完整保留出处，运行层的适用条件另写，不能改原句。

## 6. 逐问判断记录与校验

### 6.1 记录结构

实现一个精简、可扩展的JSON schema，字段职责如下；编号仅为示例，不预填真实盘面：

```json
{
  "schemaVersion": 2,
  "chartHash": "真实固定盘哈希",
  "runtimeVersion": "候选实际版本",
  "questionId": "Q1",
  "target": "原问的对象与事件",
  "dimension": "result",
  "successCriterion": "什么实际情况算发生",
  "roles": [
    {"id": "R1", "entity": "所问对象", "anchorFacts": [], "mappingSourceIds": []}
  ],
  "relations": [
    {"id": "E1", "fromRole": "R1", "toRole": "R2", "factRefs": [],
     "methodIds": [], "assessment": "supported|limited|unknown", "scope": "result|process|degree|timing",
     "reason": "简短的可核对作用说明"}
  ],
  "counterEvidence": {"status": "found|searched-none|unresolved", "refs": [], "disposition": "取舍与限制"},
  "decision": {"status": "supported|conditional|undetermined", "answer": "分项答案", "dependsOn": ["E1"]},
  "unresolved": [],
  "retrievalRefs": []
}
```

这是字段示意，带 `|` 的值表示枚举选项，不是可直接提交的实例。不得将示例里的空数组或占位文字当实际证据通过。

结果、程度、属性、身份、地点、数量、时间采用明确枚举；一个问项可关联同一盘及共用事实。角色必须引用真实盘面字段和取用依据。未取某角色说明理由，不强迫所有问题机械使用日干支年命全套。

### 6.2 程序可以验证的内容

- 固定盘哈希、版本、模块已完整加载、引用真实且已读。
- 问项ID覆盖、角色与事实路径存在、relation引用有效、结论依赖没有悬空。
- 原问判断标准没有被无记录改写；显式修改时使受影响旧记录失效。
- 相关对象已声明却没有进入任何结论依赖时，提示补查或解释替代取用；不能仅因出现“支”字就通过。
- 未解决的重要来源/位置冲突不能登记为已确认有效救应；支持和反证可以共用一条关系，不重复计数。
- 同一已修改关系的依赖结论须重新提交，包括程度和应期。计算依赖失效，不用程序判断术理吉凶。
- 无时间任务时不要求应期模块；有时间问题时，事件、尺度、触发依据和候选须登记。

### 6.3 必须保留为语义复核的内容

是否取对对象、是否真的制住、解释是否贴题、反证是否被有效回应、判断是否符合原书适用范围。程序只能提示缺项与结构问题，不能把字段齐全称为判断准确。

最强反证不存在时如实记录检索/检查范围，不制造一条反证凑格式。没有判明实际关系时允许未定，未定在质量评估中单列，不能算命中。

记录只保存判断摘要、盘面依据与来源，禁止要求输出或持久化原始私下思维草稿。客户可见内容继续遵守网站输出规范，内部模块、路径、案例ID和引用不得泄露。

## 9. 验证矩阵

### 9.1 工程与规则完整性

| 测试 | 应有结果 |
|---|---|
| 原书、books、原案例与原活动Skill保护哈希 | 与基线一致；既有外部并发修改须报告，不能覆盖 |
| 运行规则迁移完整性 | 每条有去向，例外/否定范围/来源保留 |
| 专项路由 | 单问不全库加载，多问覆盖所有实际问项 |
| 分页/模块缺失或版本错配 | 无法登记完整读取或正式提交 |
| 已读清单与实际请求文本 | 原文重组哈希一致 |
| 某角色只被命名、未用于主张 | 提示补查/说明替代取用，不能仅文字命中通过 |
| 关系依据被撤销 | 依赖的结果/程度/应期失效，必须重评 |
| 无时间问 vs 有时间问 | 前者不强配时间；后者必须有事件与方法绑定 |
| 无检索结果 | 如实记空；不得造引用 |
| 同支多标签、同案多转载 | 不计算成多份独立支持 |
| 默认legacy | 原有行为与已通过定向测试保持兼容 |
| 公开报告 | 原有内部资料与凭据边界保持有效 |

### 9.2 语义回归样例（不等于预测准确率）

至少准备以下12类输入/记录对；可使用明确标注的合成结构样例，不冒充真实课例。由执行者给出逐条预期审查理由，禁止只验证实现自己生成的同一结果。

1. 支已取宅，但结论只用人的凶吉或全局三传：应发现对象未被解释。
2. “无大灾”回答“是否任何进水”：应发现标准替换。
3. 无水临支/火在支上/辰为水库：不能单独确定无水或空库。
4. 财旺但本人取得关系受阻：不得把财存在等同到手。
5. 升职与加薪、过线与录取：分别回答。
6. 四课出现相关对象而未入传：不能自动剔除，也不能自动判成。
7. 病空、本人空、救神空：对象不同，不能同一解释。
8. 救应只缓解局部 vs 解除关键障碍：不同范围、不同重评。
9. 日干/类神/天将的十二气参照不同：不能混算。
10. 引文“仅凭A不足以定B”：不能变成“A排除B”。
11. 代问者与当事人、命支与命宫上神：不得混位。
12. 有日期候选但事件未成立：不能从日期反证事件必成。

语义审查记录“通过/失败/未定＋具体理由”。执行模型自审只是第一轮；独立复核另记身份，不能把自己复述一遍当独立评价。

### 9.3 真实模型对照计划

先做结构实验：规则内容、材料、模型版本、采样参数、工具环境、预算上限保持一致；比较当前组织、集中加载、成组模块加载。记录实际上下文差异，无法等价的样本标注，不假称严格控制实验。

再在选定结构上比较structural与enhanced，识别判断增强是否有增益。不要同时换模型、知识内容、起法和评测题而归功于合并Skill。

建议第一批24个独立事件，覆盖关系/财务/事业考试/家宅空间/疾病胎产/出行失物等，结果、程度、属性、时间分别评分。样本不足可先完成较小探索，但必须报告实际数量与分布。每版本可重复3次观察稳定性，重复运行不增加独立事件数。这个数量是启动建议，不是统计证明准确率提高的保证。

按事件划分开发和留出，阻断同案、转载、复盘、经验摘要泄露。已读过反馈或用于设计的题不能称盲测；历史文献可能被模型预先知道，注明污染边界。新增真实事件须先冻结再收反馈。

计量：逐问正确/错误/未定、回答覆盖、严重对象错误、无依据细节、规则误用、程度与应期误差、运行稳定性；再记录token、调用与耗时。未定不计正确，同时报告总体正确率与已答条件准确率，防止靠少答刷高分。小样本差异不能直接宣称胜出。

默认启用前的建议标准：所有确定工程门槛通过；规定语义回归无未处理严重错误；独立评价没有显示准确性退化，并有足够证据判断其不劣或改善。证据不足时保持候选状态；不能用“差异不显著”当作已证明不劣。

## 11. 例外处理与执行边界

| 遇到情况 | 应执行的动作 |
|---|---|
| 新旧资料冲突 | 回查来源、对象和范围；记录分歧，保留当前基线，不按新旧日期或作者人数自动裁决 |
| 缺完整盘或反馈 | 留缺口，完成不依赖它的结构/工具工作；不编造输入 |
| 文本太长/工具截断 | 分段完整读取并核覆盖，不以删掉条件来“优化” |
| 发现更方便的新架构 | 先检查是否本方案已能完成；不擅自换语言、框架或整项目重建 |
| 某个历史规则可疑 | 保留历史出处并标待核，候选运行行为明确，不静默改原文 |
| 一项来源待核 | 只冻结受影响规则/结论；继续其余已确定工作 |
| 已有用户改动或并发变化 | 重新核对，定向合并；有不可判定冲突才报告，不恢复旧快照覆盖 |
| 测试失败 | 找最小原因，修复并复跑相关项；不能删断言、放宽门槛或关闭校验过关 |
| 无真实模型实验授权/预算 | 完成离线候选与实验计划，标真实质量未测；不占用用户密钥偷偷调用 |
| 内容/工程检查已通过 | 转向交付，不反复增加无关测试或继续扩张范围 |

### 完成报告必须给出

- 实际变更文件和候选目录；活动Skill及生产是否改变。
- 版本、哈希、迁移覆盖、无损保留与实质规则变化的清单。
- 已运行命令、结果、跳过项及原因。
- 至少一个可核对的逐问记录示例；合成或真实身份清楚。
- 工程验收、语义回归、真实模型实验、独立预测准确性四种状态分别列出。
- 可复现启动命令、候选选择方式、移除候选/恢复改动的方法。
- 未定来源、未验证方法、后续启用条件。
