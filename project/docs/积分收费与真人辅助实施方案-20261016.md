# 问衡积分收费、人工充值与真人辅助实施方案

日期：2026-10-16（Asia/Shanghai）。状态：用户已批准实施，2026-10-16已上线积分改造。本文保留设计过程，最新实施状态见[上线与运营交接](积分系统实施与验收-20261016.md)。

## 1. 建议采用的完整模式

采用 **人工核实收款充值＋全站积分账户＋AI 按用量结算并封顶＋低价真人辅助**。

- 1 元＝10 积分；积分显示到 0.1 分，避免小额调用每次被取整放大。
- 免费排盘、填写资料、查看已有报告、导出、系统要求的补充资料、基础使用指导继续免费。
- 主报告建议：20 分基础服务费＋可计费用量成本的 3 倍，单次最多 80 分。
- 同事项 AI 追问建议：5 分基础服务费＋可计费用量成本的 3 倍，单次最多 30 分。
- 使用前明确提示最高费用并冻结对应额度；交付时结算，剩余自动释放。失败不扣分。
- 真人辅助建议：99 分／次，复核一个已有问题，约 10 分钟，含一轮补充解释；接待确认后服务，完成后结算。
- 抽师傅、查看联系方式、添加微信、咨询充值方式不收费。添加好友时只需备注：**问衡咨询**。
- 保留原人工支付、聚合支付、基础报告和追加次数配置，停止新购入口；已购权益正常履约。

积分改变的是结算方式与运营流程，不能据此推定原服务及收款的资质要求已经消失。网站如实说明提供的服务，不把名称替换当作资质已经解决。

## 2. 现有系统依据与改造边界

已阅读项目接手指南、最新支付记录、AI 规则核查，并检查本地账户页、支付服务、数据库迁移、AI 网关与 worker。

本轮对旧电脑服务做了只读检查：web、worker、支付补查 timer 为 active；源站 `/api/status` 返回 AI 和人工支付开启、worker 在线、聚合支付未开放。没有执行充值、付款、数据库写入或服务重启。发布版本路径没有获得有效核实结果，不沿用旧文档版本号作为当前结论。

当前可复用：账户和邮箱验证、档案与固定盘快照、异步任务和 worker 租约、后台授权、人工到账核验、旧订单退款、邀请券、审计日志。

当前必须补做：

1. `agent/gateway.ts` 的 `usage.costCny` 混合真实 token 计价与未知用量估算；`worker.ts` 又累计失败重试费用。**该字段只能继续用于成本风控，不能直接作为用户扣分依据。**
2. 现有 `entitlement_ledger` 是某档案的追问次数账，不是资金钱包；新增独立积分账，不把旧次数改名冒充积分。
3. `service.ts` 的追问依赖旧权益，worker 的追问完成也强制处理旧权益；需同时支持旧次数与新积分两种结算来源。
4. 当前永久删档会清除任务 `usage`；计费凭证须独立保存最小必要金额与计量摘要，不依赖会被清除的私密问题或报告。
5. 主 skill 截断、规则适用、证据轨迹等已有 AI 技术债仍须保留和修复。收费改造不能压缩原 skill、减少必做判断步骤或用低价缩减质量。

## 3. 积分制度与价格

### 3.1 积分账户

建议名称统一为“问衡积分”，不混用卡点、次数、余额三个单位。

| 项目 | 建议规则 |
| --- | --- |
| 兑换 | ¥1＝10 积分，¥0.01＝0.1 积分 |
| 最小单位 | 0.1 积分；数据库用整数单位保存，1 单位＝0.1 积分 |
| 有效期 | 服务运营期间无日历到期；不设置自动续费 |
| 用途 | 本站 AI 解读、AI 追问、明确下单的真人辅助 |
| 转移 | 不支持账户间转赠、交易或提现获利 |
| 退款 | 未使用的实付积分可申请核对退款；赠送积分不折现 |
| 注册赠送 | 首期不自动赠送，避免批量注册消耗 API；后台可单独发放赠送积分 |
| 默认充值 | 建议展示 ¥10／100 分、¥20／200 分、¥50／500 分，也可联系客服充值其他金额 |
| 大额充值 | 首期不主动推高额预存；单笔超过 ¥200 转人工确认，不以优惠诱导囤积 |

账户展示“可用积分”“处理中冻结”“其中实付／赠送”，不把冻结金额当成已消费。总持有积分＝可用＋各类冻结，冻结按 AI、真人辅助、退款分别列明。

### 3.2 AI 定价公式

设 `C` 为本次成功交付所对应、按有效价表核算的可计费 API 成本，单位人民币元；不是整台服务器累计 API 成本，也不是预算预留值。

```text
主报告积分 = 向上取到 0.1 分 [ min(80, 20 + C × 3 × 10) ]
AI追问积分 = 向上取到 0.1 分 [ min(30,  5 + C × 3 × 10) ]
```

其中 20／5 分为资料组织、任务运行及结果服务的基础费，3 倍为 API 成本系数，最后的 10 是元到积分的换算。公开写“基础服务费＋用量费、单次封顶”，不宣传原价转售 API。

| 服务 | 成功交付最低价 | 提交前冻结／最高价 | 使用者看到的费用说明 |
| --- | --- | --- | --- |
| 主报告 | 20 分，约 ¥2 | 80 分，约 ¥8 | 20 分起，按用量结算，最多 80 分 |
| AI 追问 | 5 分，约 ¥0.50 | 30 分，约 ¥3 | 5 分起，按用量结算，最多 30 分 |
| 真人辅助 | 固定 99 分，约 ¥9.90 | 99 分 | 一个已有问题，约 10 分钟复核 |
| 网站使用指导 | 免费 | 不冻结 | 如何排盘、充值、查看报告等 |

历史合成验收样本仅用于演算，不能当作平均成本、供应商最终账单或准确率：

| 历史任务 | 当时程序估算 API 成本 | 按建议公式演算 |
| --- | --- | --- |
| 主报告 | ¥0.746824 | 42.5 分，约 ¥4.25 |
| 追问 | ¥0.48434048 | 19.6 分，约 ¥1.96 |

高成本任务仍按用户封顶价结算，差额由平台承担；不得跑到一半临时加价。现有内部 API 成本上限主报告 ¥6、追问 ¥1.5 与用户积分封顶是两套不同控制，不能把用户积分上限误作为减少判断步骤的理由。上述价格未覆盖所有失败、人工、服务器及售后成本，需靠试运营数据复核。

### 3.3 为什么暂不采用另外两种方式

| 模式 | 适用情况 | 本次取舍 |
| --- | --- | --- |
| 固定次数价 | 简单，但轻重问题同价、仍需处理次数包 | 作为独立备用计费模式保留，不作为推荐主模式 |
| 按 API 请求次数 | 不同请求长短差异大，工具往返会增加次数 | 不采用，不能把一次底层请求等同一次用户咨询 |
| 纯 token 无封顶 | 计量细，但使用者无法提前确定最高费用 | 采用用量计费，同时加基础费和最高价 |

如果上线前还不能准确区分已知与未知用量，先关闭按量模式；确需先开放时，可另选“主报告固定 50 分、追问固定 20 分”的明确固定价模式，页面和订单必须标明固定价。不能在用户选择按量后静默改成固定价或拿估算额扣费。

### 3.4 试运营调价条件

累计至少 30 个成功主报告、30 个成功追问，再比较 P50/P90/P95 API 成本、失败成本、封顶比例、时长与人工售后投入。该样本量只是初步运营观察，不证明统计稳定。

封顶比例超过 20% 或计入失败后的总贡献连续为负，调整新订单价格或暂停新任务；不追溯加收已确认的费用。失败率或 AI 质量问题先修系统，不靠删 skill 降成本。

## 4. 人工充值机制

### 4.1 用户流程

1. 登录并验证邮箱，进入“账户 → 积分与充值”。
2. 页面生成绑定该账户的“充值识别码”，用户一键复制；不要求把邮箱密码发给客服。
3. 展示官方充值微信／二维码。添加好友备注只写“问衡咨询”；添加后再发送充值识别码和希望充值的金额。
4. 运营者告知金额并核实真实收款，后台给对应账户充值。
5. 用户在站内收到入账提醒，看到实收金额、增加积分、入账时间、参考编号及可用积分。邮件可选，失败不影响入账。

首期不再要求每次 AI 使用都提交付款截图。充值只人工核验一次，随后平台自动扣分。

### 4.2 后台操作

入口：“运营后台 → 积分管理”。按充值识别码、账户 ID 或邮箱精确查找账户，显示名称和脱敏邮箱，防止充错人。

后台提供三种独立操作，运营者可以自选积分数量：

| 类型 | 必填内容 | 入账与退款属性 |
| --- | --- | --- |
| 实付充值 | 实收金额、到账渠道、真实交易参考、目标账户 | 按 1:10 自动计算；积分可输入但必须与金额一致，可核对退款 |
| 赠送／补偿 | 自定义积分、原因 | 记录赠送来源，不伪造现金收入，不折现 |
| 错账纠正 | 原流水、纠正数量、原因 | 追加冲正流水；不直接编辑余额或删除历史 |

提交前展示“账户＋原可用积分＋本次增加＋充值后积分＋实收金额”，再次确认后原子入账。交易参考在同一收款渠道唯一，重复点击、刷新或重复登记同一收款不重复充值。

误充积分已消费时不得直接扣成负数；暂停该账户新增消费、保存差额与纠正待办，人工核对处理。不能通过“赠送”类型伪装实收收入或绕过真实到账。

后台保留每次操作的管理员、时间、原因与前后变动；对外展示脱敏参考，不公开完整微信、支付宝实名或收款截图。不要要求上线时重新填写可安全复用的既有配置。

### 4.3 联系方式未配置

官方充值微信默认为空，页面显示“充值联系方式待配置，暂未开放充值”；不显示虚假微信号，不开放可支付申请。可先完成页面和后台功能，真实联系方式配置后再开放。

五位师傅的联系账号与“官方充值微信”分开配置。未来可填同一个微信，但师傅卡片不自动获得可宣称官方收款的权限。

## 5. AI 消耗、退回与计量

### 5.1 一次用户操作如何结算

```text
确认本次最高费用
  → 数据库事务检查余额并冻结
  → 保存价格、价表、问题版本与固定盘快照
  → 创建唯一任务与 outbox
  → 排队／执行
  → 成功：报告入库与积分结算同一事务提交
  → 失败／取消且未交付：释放全部冻结
```

- 一次完整分析即一个计费操作，包括正常的多次模型往返、子会话检索和最终整理，不逐个工具弹出付款。
- 充值 ¥10 获得 100 分；先冻结主报告 80 分，若实际结算 42.5 分，释放 37.5 分，最终可用 57.5 分。
- 用户余额少于最高冻结额度时，先提示充值；不能默认透支，也不为了低余额私自减少分析内容。
- 同一档案同时只跑一个任务。不同档案共享钱包，冻结必须锁账户校验；所有 AI、真人辅助及退款模块采用一致锁顺序，避免互锁或超扣。
- 浏览器重复提交使用同一幂等键，不能生成多个冻结或多个结算。
- worker 失联必须先回收租约、隔离旧 worker 的交付权限，再释放冻结；旧进程迟到不能写报告或重复扣分。
- 排队超过 30 分钟仍未启动，可取消释放；执行中保留现有超时控制。刷新、断网、关页面不算取消，用户可回档案查看结果。
- 未交付时用户可取消，平台不扣分，已产生 API 成本记运营成本；每日最多 3 次主动取消运行中任务，之后需客服核对，避免反复制造成本。

### 5.2 哪些调用可以计费

`api_usage_events` 逐条记录任务、attempt、子会话、内部请求标识、供应商响应 ID、模型、输入／缓存／输出 token、价表版本、已知／未知用量及是否可计费；不保存密钥或原始思考内容。

- 成功交付的最终有效 attempt 中，正常完成的主／子会话模型调用可计费；工具本身不再另收请求费。
- 失败 attempt、超时、输出截断后修复、系统自动重试、被丢弃的重复结果均不向用户收费。保留为运营成本，不能从记录中抹掉。
- 同一成功 attempt 内失败调用及其失败输出不计费；最终采用的有效调用正常累计。
- 供应商返回 input/output/缓存分项时分别计价；确认缓存命中与未命中不重复累计。思考 token 若已包含在输出计费数中，不另加一遍。
- 不同模型、价段、币种使用对应有效价表与汇率快照；首期只开放已验证计量的官方模型。不能把历史代码中的高峰价当作当前最终账单。
- 若渠道只有价表估算、没有可逐笔对照的实际扣费，页面称“按 API 返回用量及公示价表核算”，不宣称与供应商最终财务账单完全相等。
- 成本使用定点高精度值；全部可计费请求汇总后，只做一次 0.1 积分向上取整，不逐请求取整。不用 JavaScript 浮点累计钱包金额。
- 内部请求标识确保重复处理同一调用只计一次；同一供应商响应不可重复入账。真实再次发出的网络请求保留独立事件，根据重试分类决定是否计入用户费用。

### 5.3 未知用量、澄清与退回

| 情形 | 用户费用与处理 |
| --- | --- |
| 用量缺失／无效／worker 崩溃估算 | 未知部分由平台承担，只结算已验证的有效用量；明细标注缺失部分未计费，不用预留金额补扣 |
| 成功交付但全部用量缺失 | 只收已公示的基础服务费；产生计量告警，停止接纳新的按量任务直到修复 |
| 系统要求补充人物、年份或事情背景 | 不单独收费；本轮仅澄清则释放冻结，补充后沿用同一计价快照重新冻结，最终交付再结算；之前澄清成本由平台承担 |
| 系统补充资料超过 2 轮仍不完整 | 停止任务并释放，不自动创建新的付费追问 |
| 用户在报告后提出新的实质追问 | 明示本次最高 30 分并确认，属于新计费操作 |
| 删除尚未交付的档案 | 取消任务、撤销交付权、释放冻结；已交付并消费的金额不自动退回 |
| 已交付内容不可用或费用有争议 | 售后核对，可部分／全部退回积分；用反向流水关联原结算，不改历史账 |
| 免费重看／导出／基础使用答疑 | 不产生模型任务，不扣分 |

若缺失、失败用量占比过高，暂停按量计费；不能通过反复只收基础费掩盖计量故障。成本风控账与用户积分账分别留存、定期对账。

### 5.4 退款与账户删除

- 实付与赠送分账，首期扣款按实付充值批次 FIFO，再使用赠送余额；结算必须记录分摊到各批次的数量。发生退积分时恢复原来的实付／赠送属性。
- 原有订单退款仍走原渠道和原规则。新充值退款按尚未使用的实付积分计算，0.1 分对应 ¥0.01；不收隐性退款费，不退超过原实收金额。
- 申请现金退款时先冻结相应可退款积分；运营者实际退款并核实交易后再登记完成，不能仅点击按钮就声称资金退回。退款失败或撤销则解冻。
- 同一积分不能同时给 AI、真人辅助及退款冻结。赠送积分不可现金退款；首期不开放充值附送活动，避免附送回收规则不清。
- 注销前完成有效任务结算、冻结释放和未用实付积分退款；必要交易记录与私密报告分离。删除报告不能删掉已发生的财务事实，也不能恢复已经退款的权益。

- 用户主动点击“开始抽取”，再点击“停止”；服务端保存等概率结果，动画缓停并准确停到对应头像。与首页排盘的固定盘、报数、月将完全解耦，不复用排盘 ticket。
- 抽取免费，可重新抽取，不限制必须接受某一个结果。刷新保留最近一次结果，减少重复操作。
- 抽中后展开头像、名字、联系账号、二维码（可选）、“复制微信”“复制备注”。添加好友备注固定为“问衡咨询”。
- 未配置账号时仍可以展示抽中身份，但明确显示“联系方式待配置”，不提供复制假账号或付费按钮；不偷偷重抽到已配置者，保证公布概率真实。
- 5 位都显示，不虚构忙闲状态。需要暂停时由后台明确设置暂停接待，结果页展示状态且不收费。
- 免费抽取与重新抽取做轻量限流；不能设计成充值抽奖，也不把抽中某位解释为更高准确率。
- 桌面圆盘配结果卡；手机圆盘上下布局，适配小屏；减少动态偏好下直接展示结果，键盘和屏幕阅读器可操作。

### 6.3 真人辅助服务规则

推荐页面文案：**“不确定如何理解报告？可以预约真人协助梳理问题、复核盘面和解释术语。”** 不承诺保证预测正确或量化提升准确率。

| 项目 | 首期建议 |
| --- | --- |
| 使用指导 | 免费，只讲网站操作、费用和已有功能，不替代完整人工分析 |
| 轻量真人复核 | 99 分，约 ¥9.90；一个已有档案、一个核心问题、约 10 分钟，含一轮补充解释 |
| 不包含 | 新事项完整人工起课、长期陪聊、无限追问、包成功承诺 |
| 入口 | 报告页“请真人协助”、账户页“真人辅助”；未完成 AI 报告先提供免费使用指导 |
| 预约条件 | 已登录、已验证邮箱、对应联系账号已配置、接待已开启、积分足够 |
| 接单时间 | 建议 24 小时内接单；超时自动释放，暂未接单可随时取消 |
| 服务时间 | 接单后 24 小时内完成；后台可提前关闭接待，不展示虚假即时在线 |

具体流程：免费抽取 → 免费查看联系方式 → 选择已有档案与要复核的问题 → 显示 99 分固定价和服务边界 → 用户确认并冻结 99 分 → 生成辅助服务编号 → 用户添加微信（备注仍只写问衡咨询），添加后发服务编号 → 运营者后台接单 → 提供服务 → 提交服务摘要并标记完成 → 用户确认后结算。

用户从未加微信、仅看到联系方式、仅抽取、尚未创建付费辅助单时，均不扣积分。充值咨询与免费操作指导也不通过付费辅助单计费。

状态：`待接单 → 已接单 → 待用户确认 → 已完成`，另有`已取消／已超时／有争议／已退回`。

- 接单前取消／24 小时未接单：全额释放。
- 已接单但未提交服务成果即超时：全额释放；若确需改期，须用户在站内明确同意，不能后台无限延期。
- 提交成果后用户有 48 小时确认或提出异议；提交前已明示，且站内发送完成提醒。无异议可自动结算，异议则停止自动结算，转待处理。
- 争议持续 7 天未处理：默认全额释放，运营者仍可更早退回。售后不得无限冻结积分。
- 对已接单的取消请求：转售后处理；未提供服务原则上全额释放，已有部分交付须用户明确同意部分结算，不能只以“已接单”为由扣满。
- 微信沟通只发必要的档案编号／服务编号。对外共享报告由用户另行确认，不自动生成公开链接或把客户资料发给其他人。
- 外部微信聊天无法由网站自动证明交付；后台保留接单、服务摘要、用户确认及争议记录，不能把复制微信号当作完成证据。

### 页面分区

1. **账户概览**：可用积分、冻结分类、实付／赠送、任务与预约状态、档案容量；账户 ID 与便于客服识别的充值码。
2. **积分与充值**：固定兑换率、建议金额、官方微信／二维码、复制“问衡咨询”、充值码和历史入账；说明人工核实后到账，不虚构秒到账。
3. **消费明细**：按充值／AI／真人／退回／调整过滤；每条显示时间、关联服务、实际扣分、释放数量、余额。正常列表以净变化为主，展开才看冻结与结算细节，避免看起来扣了两遍。
4. **真人辅助**：五位头像转盘、抽中结果、联系方式、99 分服务说明、预约列表与取消／确认／异议入口。
5. **我的档案**：继续复用档案列表、固定盘、收藏、导出、删除；报告旁增加“本次消耗”链接。
6. **账户设置**：验证邮箱、修改邮箱、密码、可选 TOTP、注销独立页面，不再与充值订单混成长页面；普通用户也可自选开启 TOTP。
7. **历史订单**：仅对存在旧订单／权益的用户显示旧订单和剩余追问；聚合支付流水作为历史详情，普通用户默认不再看到旧收银台入口。

支付成功与消费成功分开表达：“充值到账＋100 分”“解读完成－42.5 分”。冻结写“暂存额度，不是已扣费”。不足时说明具体差额，并保留已填问题，充值回来可继续，不丢草稿。

充值页建议文案：

> 问衡积分用于本站解读与真人辅助。1 元＝10 积分，按需充值即可。添加客服微信时，请备注「问衡咨询」；添加后发送本页充值识别码。我们核实实际到账后为你的账户充值。

扣费确认示例：

> 本次主报告 20 积分起，按实际用量结算，最多 80 积分。开始后先暂存 80 积分，完成后退回差额；未完成不扣分。

## 8. 原收费体系保留与切换

采用独立开关与任务快照，不能只是用 CSS 隐藏按钮：

```text
billingMode = legacy | points
legacyNewOrdersEnabled = false      # 积分切换后拒绝新建旧套餐订单
legacyFulfillmentEnabled = true     # 继续履约原订单、退款和旧次数
pointsTopupEnabled = false          # 联系方式、对账及验收齐备后再开
pointsAiEnabled = false             # 计量与扣费验收后再开
humanAssistEnabled = false          # 真实联系账号配置后再开
```

- 保留旧数据库、支付接入代码、加密配置、签名／回调／查单、补查、退款及后台，只暂停新购与普通用户入口。历史支付记录仍可访问。
- 切换前盘点未付／已付／退款中／执行中订单。已创建未付订单不直接删掉，明确截止时间和是否继续接受；已经打开收银台的迟到付款仍按旧流程核实并履约或退款，不能静默丢弃。
- 已付主报告按原合同交付，已购剩余追问继续免费抵用；旧权益优先，不同时扣积分。
- 旧权益用尽后，用户明确选择新积分追问，不再需要买 3 次包。每次任务只允许 `legacy_entitlement` 或 `points` 一个资金来源，不能运行中切换。
- 新积分任务不沿用旧“最多 8 次”作为购买门槛，继续限定同一事项、输入长度、上下文与频率；不无限堆叠历史，也不默默丢弃关键上下文或重新起课。超出处理能力时明确提示整理问题／新建档案。
- 旧次数不强制折算积分，不猜每个旧追问的货币价值，不因旧收银台隐藏导致无法使用旧权益。
- 邀请券保留。停止对新注册继续发放旧套餐券，旧已发放未用券可抵一次积分主报告八折；不抵充值、真人或追问，不兑换现金。已有邀请关系仍保留原履约奖励承诺，符合条件时仍补发一次对应八折权益。
- 邀请券冻结与钱包冻结同事务，失败退还券；对有券的主报告按最高 64 分冻结，实际公式先应用 80% 再统一向上取到 0.1 分。此前已按旧订单冻结的券仍依原订单状态处理，不能在两套系统同时使用。
- 紧急回退先停新积分消费，继续结算或取消在途任务，再切兼容代码。不能直接回滚到不认识钱包的旧 worker，也不能回灌旧数据库覆盖真实充值；钱包和历史记录始终可查询。

## 9. 工程结构与配置草案

以下是实施设计，尚未创建数据库迁移或 API。

### 数据

| 新结构 | 责任 |
| --- | --- |
| `point_accounts` | 用户实付／赠送可用与冻结，非负约束，带版本／行锁 |
| `point_ledger` | 不可变流水，记录来源、实付／赠送属性、可用／冻结变化、幂等键与余额快照 |
| `point_lots`、`point_allocations` | 充值批次、退款剩余金额、消费分摊和原属性返还 |
| `point_topups` | 人工实收金额、渠道、唯一到账参考、管理员与入账状态 |
| `point_holds` | AI／人工／退款冻结，金额、租约／到期、释放／结算终态 |
| `billing_operations` | 唯一用户操作、任务关联、费率／封顶／券快照、结算摘要；不随删档清除金额凭证 |
| `api_usage_events`、`model_price_versions` | 逐请求真实用量、成功／失败／估算分类、价表和核对依据 |
| `advisor_profiles`、`advisor_draws` | 五个固定身份、图片焦点、公开联系方式、接待开关、免费抽取结果 |
| `human_assist_requests` | 预约、关联档案、服务范围快照、冻结、接单／完成／争议状态与时间 |
| `point_refunds` | 未用实付积分退款申请、冻结、真实退款参考和结果 |

也可在现有 `service_settings` 存师傅与价表设置，但必须做版本和公开／私有字段过滤。五张头像作为持久静态资产发布，不依赖微信本地临时路径。

### 接口边界

- 用户：读取钱包／积分流水／充值记录、读取公开充值联系配置、获取自己的充值识别码、确认 AI 报价并冻结、申请退款；不能自行确认充值或写余额。
- 真人：免费抽取、读取结果、预约／取消／确认完成／提出异议；服务端验证档案所有权及配置可用性。
- 管理员：查询账户、确认实付充值、赠送／冲正、真实退款登记、师傅账号与接待配置、辅助接单／提交成果、价表和功能开关。
- 所有变更复用现有登录、验证邮箱、同源防护、权限和限流；用户只读本人财务与档案。管理员敏感操作复用已有会话验证，不恢复此前用户已取消的强制 TOTP 前置。
- 幂等与钱包变化必须在数据库事务内完成；异步任务通过 outbox 发布，禁止“先扣余额再尽力发队列”。异常恢复依赖持久状态而非浏览器定时器。

配置草案：[积分与真人辅助配置草案](积分与真人辅助配置草案-20261016.json)。所有微信号与二维码均为空，所有新服务开关默认关闭；不是已经导入网站的运行配置。

## 10. 实施次序与验收

1. **积分基础**：独立账本、实付／赠送分账、后台人工充值／纠正／退款、账户余额与流水。全部在隔离数据库验证。
2. **计量与 AI 接入**：逐请求计量、可计费与运营成本分开、价格快照、冻结与交付事务、worker 幂等恢复、旧权益兼容；先做模拟异常，再做受控真实 API 小样本核对。
3. **账户与页面**：新的账户导航、充值页、消费详情、报告费用确认、旧订单历史；保持中英文与手机可用。
4. **真人辅助**：五位原图、独立转盘、空联系方式状态、固定价预约、接单／完成／争议／超时释放。
5. **切换**：盘点旧单、数据库备份、新结构向前迁移、兼容 worker；仅在无活跃任务或有明确恢复方案时更新 worker。界面发布按既有独立 release 方式，保留其他网站与旧支付配置。

上线验收至少包括：

- 同一真实到账参考并发登记只充值一次；充错账户的冲正可追溯，实付金额与积分严格一致。
- 两个任务与人工预约并发时不能超扣，积分不能为负；重复完成／取消／退款只有一次结果。
- 成功报告与扣分同时入库；崩溃、租约丢失、任务重投、迟到 worker 均不重复扣分或提前释放仍有效的冻结。
- token 缺失、缓存、思考输出、失败调用、子会话、自动重试和价格变化不会造成重计或估算扣费；逐条用量汇总可对账。
- 账号 A 无法充值确认自己、看 B 的明细、消费 B 的钱包或用 B 的档案预约；普通用户无法访问运营写接口。
- 澄清、失败、删档、取消的冻结准确释放；充值现金退款与消费返积分分别正确，不因删除客户报告丢账。
- 五张头像顺序正确；五位均 20%，动画指向与保存结果一致；免费抽取和复制联系方式不扣费。
- 联系方式为空／暂停接待时不生成付费真人单；未接单、未交付和争议都有到期处理，不永久冻结。
- 旧报告与剩余追问正常使用，旧权益优先且不扣积分；新建旧套餐 API 真正关闭，旧回调和退款继续工作。
- 旧邀请权益可履约，券不能在新旧系统重复使用；费率修改不追溯既有报价。
- 手机页面、键盘操作、减少动画、中英文、账户退出和敏感页不缓存均检查；新配置不泄露私有字段。

本阶段只完成方案、头像归档与空配置草案。真实微信号、二维码和营业时段后续可在后台配置；缺少这些资料不妨碍独立开发，但不应开放对应的收款／付费辅助。
